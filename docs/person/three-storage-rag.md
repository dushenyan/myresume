# 三存储 RAG 架构：让每类数据待在合适的地方

> 项目：government-advanced-rag（政务 RAG 知识库系统）

## 从最简单的方案说起

大部分 RAG 教程，第一版都是这样的。

所有东西塞进一个向量库：文档切块，算出向量，存进去。查询时把问题也变成向量，找出最相近的几块，扔给大模型生成答案。

三天能跑通，一周就会遇到麻烦。

第一个麻烦是精确词。用户搜“GB 50352”，语义模型未必能对上《民用建筑设计统一标准》。编号、型号、人名这类硬关键词，向量检索经常失手。

第二个麻烦是管理。知识库有几百个文档，哪个发布了、哪个作废了、属于哪个类目，这些都是结构化信息。向量库管理这类信息很别扭。

第三个麻烦是多跳问题。“张三负责的项目引用了哪个标准？”这类问题要先找到张三，再找到项目，再找到标准。答案散落在不同文档里，靠向量相似度串不起来。

这三个麻烦，对应三类性质完全不同的数据。

## 图书馆的类比

把 RAG 系统想象成一座图书馆，需要的正是三套设施。

MySQL 是登记台账。哪个书架、哪本书、谁借走的，一笔一笔记得清楚。台账擅长管理结构化信息，不擅长找内容。知识库、文档、发布状态这些元信息，交给它。

Elasticsearch 是检索柜台。既能按书名找，也就是全文检索；也能按“意思”找，也就是向量检索。一个索引里，两种卡片都放。

Neo4j 是人物关系网。张三认识李四，李四负责 B 项目，一张图把线索串起来。多跳问题靠它回答。

三种数据库不是技术栈的堆砌，而是分工。每类数据待在最合适的地方，这就是三存储架构的全部出发点。

## 为什么 BM25 和向量要放在一个索引里

全文检索和向量检索，是两种互补的能力。

BM25 靠词频匹配，擅长精确词。标准编号、产品型号、专有名词，它一抓一个准。但它不理解语义，“电脑蓝屏”匹配不上“显示器故障”。

向量检索靠语义相似，擅长模糊表达。换个说法也能找到相关内容。但它对精确词不敏感，而且语义相近不等于答案相关。

我在 Elasticsearch 的同一个索引里，给 chunk 建了两类字段：text 类型放全文，dense_vector 类型放向量。一次查询同时召回两路结果，再融合排序。

向量模型选的是 bge-small-zh-v1.5 和 bge-base-zh-v1.5，中文语料，用 SentenceTransformer 加载，并开启 normalize_embeddings。向量的模长归一了，相似度才有可比性。

## 召回求快，精排求准

两路召回之后，问题还没完。

召回阶段的目标是“别漏”，宁可多捞一些候选。但候选一多，排在后面的往往是凑数的。直接把几十个候选塞给大模型，既浪费 token，又干扰生成。

所以需要第二阶段：精排。

我用的是 bge-reranker-base。它是一个 BERT 分类模型，输入一对文本——问题和候选 chunk，输出一个相关性分数。对召回的前二十个候选逐一打分，只留最高的五个注入提示词。

这里有个容易被忽略的细节。喂给 rerank 模型之前，必须用 tokenizer 把问题和文本编码成一个 pair，并且调用 model.eval()。不然 Dropout 和 LayerNorm 的行为与训练时不一致，分数会掉。

精排不是免费的，它要完整跑一遍 BERT。所以什么时候上精排，是个工程判断。

我的原则是看场景。专业库、客服这类高精度场景，强制走精排，把 Top-5 命中率提上去。通用对话场景，只做混合检索，把延迟和算力成本压下来。

一句话：召回阶段求快，精排阶段求准，要不要精排看业务。

## 模型只加载一次

embedding 模型和 rerank 模型，动辄几 GB 权重。加载一次要几十秒，还要初始化 GPU。

如果每个请求都加载一遍，服务基本没法用。

我的做法是把加载放到服务启动时，模块级全局实例共享一份。请求进来直接用，内存里始终只有一份数据。

部署还要考虑设备差异。办公室的机器只有 CPU，服务器有 cuda 显卡，Mac 上是 mps。我写了一段自适应逻辑，启动时探测可用设备，选择最快的那一个。同一份代码，三种环境都能跑。

## 代码怎么分层

工程结构上，项目分了两个应用模块。

apps/knowledge 管知识库：建库、传文档、发布下线。apps/engine 管 RAG 引擎：解析、分块、召回、精排、生成。两者共用 common 层的数据库、ES 和配置。

引擎不关心知识从哪来，知识模块不关心检索怎么做的。将来要加新的文档格式，只动 engine；要接新的管理后台，只动 knowledge。

另外配了一个 demo.ipynb，交互式验证全链路。调分块参数、换向量模型，先在笔记本里跑，看结果直观，确认了再进代码。

## 分块时为未来留接口

RAG 的效果，一半取决于检索，另一半取决于分块。

我用 pdfplumber 解析 PDF，按重叠窗口切块。相邻块之间留一段重复文本，防止一句话被切断后两边都失去上下文。

chunk 表里除了文字内容，还存了三样东西：页码、关联图片的路径、关联表格的路径。

当前版本只用页码做溯源，图片和表格暂时闲置。但表结构先留好了。将来要做“回答时引用原文图表”，只需要读这几列，不用重构数据。

设计的时候多想一步，将来就少动一次结构。

## 图谱层的定位

说实话，Neo4j 这一层目前还在规划中。

把它写进架构，是因为多跳问题是真实存在的需求。向量检索解决“找相关”，解决不了“顺着关系走两步”。实体关系图谱天然适合这类查询。

所以我把它定位成预留的出口：元数据和全文检索先跑起来，图谱层等业务真正需要多跳问答时再补。架构图上画了它，代码里给它留了位置，但没有为了凑数而提前堆功能。

没做完的部分，就明说没做完。这比编一个“全部落地”的故事要可靠得多。

## 小结

三存储架构的本质，不是用了几个数据库，而是想清楚了三件事。

元数据要事务和关系，交给 MySQL。全文和向量要检索速度，交给 Elasticsearch。实体关系要多跳查询，留给 Neo4j。

再往上一层，是两个工程判断：召回和精排怎么分工，模型什么时候加载。

技术选型没有标准答案，只有“这个数据是什么性质、谁来管它最合适”。想清楚这个问题，存储方案自然浮出水面。

数据库没有好坏，只有合不合适。
