- 节点执行到一半进程崩了，重启后恢复的确切语义是什么？会重复劳动吗？
  从该 thread 最新 checkpoint 恢复，已完成节点不重跑、不重复计费；当前未完成节点整体重跑，因此节点内检索动作先查 URL 去重缓存再发起，重复成本被去重兜住。
  @frame: 205ec5ee-0a71-4607-9377-c7262dbc8c09
- Checkpointer 对状态数据有什么要求？自定义 reducer 是干什么的？
  状态必须可序列化（JSON 友好），所以来源清单存结构化小对象而非文件句柄。reducer 决定同名字段的合并策略：默认覆盖，笔记/来源这类累积字段用追加型 reducer，多写入方不互相踩。
  @frame: bcef6ddd-e49a-488c-8a0b-f0b3ecd1a9e5
- 生产环境 Checkpointer 用什么后端？为什么不是内存版？
  内存版重启即丢 checkpoint，断点续跑形同虚设；生产按恢复需求选：单机 SQLite 起步，多实例共享与水平扩展用 Redis/Postgres saver，同时约束 checkpoint 保留数量防膨胀。
  @frame: 0f97401f-d7b2-4b87-90b3-70124a9d7c10
- 多轮长任务状态只会越来越大吗？膨胀怎么治？
  会，需要主动治理：笔记存摘要而非检索原文全文；来源只存元数据（URL/时间/摘要）正文按需拉取；超预算触发历史笔记二次归并，保留来源 ID 引用不断链。
  @frame: 58f09805-607d-43cf-a3b1-65ef0f934201
- 高并发下同一用户开多个会话，或不同用户同主题并发，隔离怎么做对？
  双重隔离：请求级依赖注入把 session 绑到调用链，Redis 键全部带 session 前缀，任务各自独立 thread_id；同主题并发只有来源缓存可能共享，且缓存只存公开检索结果、不含会话上下文，无泄露面。
  @frame: 400128a0-53e2-4350-b1f2-241214d61c81
- 有限重试的参数怎么定？哪些错误重试有用，哪些该直接降级？
  瞬时性错误（超时/限流/5xx）做指数退避重试 2-3 次；确定性失败（URL 404、解析异常）不重试直接降级；重试上限按「单源抖动不该拖长整体任务」取，超过即空结果兜底，缺信息由下一轮补检自然吸收。
  @frame: 331e1b40-8916-4ee9-bd7f-d8ab427ec1c6
- 引用合法性「由代码把关而非模型自觉」，具体把关到什么程度？模型伪造一个看起来合理的来源怎么办？
  结论携带的来源 ID 必须在去重后的真实来源清单里存在，不存在则该结论自动降级标注「模型推断」。伪造 ID 过不了白名单校验；伪造「URL 看起来真」堵不住，靠来源清单只能来自真实检索结果（爬取过程留快照）来断根。
  @frame: 12a8df44-8ab6-4cfb-b064-7e9f5819f964
- 置信度「基于来源时间分布确定性计算」，给出你的计算要素设计？
  四个可复现要素：去重后来源数量、来源发布时间分布（越近权重越高）、多来源交叉印证度、信息缺口覆盖率。纯函数式计算，同输入同输出，分档结果映射到报告显式标注。
  @frame: 1caa59bc-b0e4-49a6-b619-a4b32d11d389
- 提示词灰度按什么维度分流？效果用什么指标归因？
  按版本标签 + 会话 ID 哈希分流，同一角色新旧模板并行。归因指标全部已有埋点：Judge 收敛轮数（提示词是否引导更有效检索）、格式失败率、引用准确率、人工抽检可用性；单角色单变量，避免多改动同时上线污染归因。
  @frame: bd6ed309-7bf9-44d4-8f8c-13404761c410
- 格式解析失败自动修复重试是怎么做的？修复失败后呢？
  解析失败时把原始输出+报错信息回填提示词让模型自修复一次；再失败则该节点降级——Keyword 降级用上一轮遗留词、Judge 降级判不足继续循环、Report 降级基于已有笔记出稿，单点格式失败不杀全局。
  @frame: 29c8ec66-bc93-48ed-b7b8-db4397c7a953
- 单模型和多模型混用怎么权衡？哪些节点值得换小模型？
  按节点任务类型定价：Keyword/Judge 是模式化短任务，小模型即可且更快更便宜；Summary/Report 吃理解与整合能力保留大模型。路由在节点内配置，编排层不感知，换模型不影响控制流。
  @frame: 060915b5-455a-408b-a026-89aa25093e32
- 为什么置信度宁可用确定性公式也不让 LLM 打分？除了贵还有什么？
  三个硬伤：不可复现（同报告两次打分不同，回归无法做）、模型自评对幻觉不敏感（它不知道自己编的）、不可解释（审计时说不清分为什么是 0.7）；确定性公式每一项都能溯源到数据。
  @frame: 6da1e8ab-296b-4165-8743-e4c9b1c9f80f
- 你压测过这个系统吗？并发能力瓶颈在哪？怎么测出来的？
  瓶颈不在 FastAPI 在外部：LLM 限流配额和检索源 QPS 决定上限，本地压只能测出连接池与 Redis 余量；测法是录制真实模型/检索响应做 mock 后端压全链路，线上按租户配额隔离。
  @frame: a5bd9bd5-00e1-4fc3-b779-b20db781f418
- LLM 输出带 Markdown 包裹的代码块、JSON 外面套解释文字，这类脏输出怎么处理？
  不靠正则在主链路硬削：主防线是 function calling 参数约束（输出直接落在结构化字段里，脏文本概率大降）；残余包裹在解析层做一层提取容错，提取失败才走修复重试。
  @frame: 3be555a9-f36c-4afe-9ae0-251e8c98837a
- 多轮任务的成本失控怎么防？只靠 max_rounds 够吗？
  不够，轮数只控次数不控体量：另设任务级 token 预算熔断，超预算强制进 Report；每轮成本（检索次数 x 笔记长度 x 模型单价）在进度事件里显式上报，触顶和熔断了用户才知道为什么停。
  @frame: 5c681db2-644a-40cf-9a55-99ac3937552a
- 这个系统最大的未知风险，或者说最可能在生产环境爆炸的点，是什么？
  检索源质量退化：劣质/过期来源会同时骗过 Judge 的充分性判断和报告的引用校验（ID 合法但内容烂），形成「格式全对结论错」的静默故障；缓解靠来源时效权重与人工抽检兜底，这是没完全解决的问题。
  @frame: 0243c963-3c63-44f7-ad9a-7b658c59d709
- 如果让你给 Judge 加「反谄媚」机制——模型倾向于判「充分」提前收工，你防吗？怎么防？
  会防：Judge 输出结构化信息缺口清单，缺口非空即强制补检，路由不信它的「充分」枚举值单一信号；监控 Judge 首轮即充分率，版本化后对比——这个指标异常上升说明它在偷懒，要换判据。
  @frame: 75ac64f8-fe55-44c2-be20-23a256243fe6
- 重来一次，你会最先改掉现在设计里的哪个决定？
  把 Judge 的「充分/不足」事后再补检改成前置缺口建模：第一轮后就维护结构化 gap 清单，检索围绕缺口收敛而非每轮重新想词——能降轮数成本和 Judge 偷懒空间；其次是检索 fan-out 并行，时延收益比看起来大。
  @frame: 360325bc-c4df-4e11-b1bd-76f2473e4eb6

- 为什么选 LangGraph 而不是 AutoGen / CrewAI 这类对话驱动多 Agent 框架？
  需求是确定性控制流的回环 + 断点 + 审计，对话驱动框架的控制流由模型协商决定，难单测难复现；LangGraph 把控制流交给图拓扑和代码，语言任务只占节点，恰好是本项目要的反向选择。
  @frame: dca07743-21e4-487d-93e7-52e262823aa2
- 和 Temporal / Airflow 这类通用工作流引擎比，LangGraph 赢在哪？输在哪？
  赢在 LLM 生态原生：状态 schema、结构化输出、reducer、checkpoint 都为语言任务设计，自接 LLM 后端要重写这一层；输在通用性：没有它们的跨语言/强一致性/长周期定时器能力，但秒级到分钟级的调研任务用不到那些保证。
  @frame: 32bcc032-cba4-4a67-8945-1cb915643c7e
- 自研一个编排框架要补上哪些能力才能达到 LangGraph 的可用度？为什么选择不造？
  至少要：类型化状态 + reducer 合并、条件路由、可插拔 checkpoint 后端、中断恢复语义、可视化拓扑；这些恰好是最难测对的部分（恢复语义边界情况）。选型判据：核心差异化在 Agent 分工与质量策略，不在调度本身。
  @frame: f2b9cdf0-4825-49be-9216-fe0963be699d
- 设计一个你理想的 Checkpointer 存储层：序列化格式、隔离、保留策略、清理怎么定？
  序列化用 JSON + schema 版本号（旧 checkpoint 可识别可迁移）；键按 thread 前缀隔离；保留最近 N 个 + 终态报告另走归档（归档是业务数据不走 checkpoint）；清理按会话 TTL 带钩子，删前校验无进行中任务。
  @frame: 85f33830-3dbb-4fb9-a1d8-49fd1a6455e6
- 如果要把系统从单团队工具升级为多租户 SaaS，最先崩的是哪块？怎么改造？
  隔离粒度会从 session 不够到 tenant：模型配额、检索源凭证、Redis 键空间都要升租户维度；最先崩的是资源层——单 LLM 配额被大租户打爆、单检索源被限流；改造为租户级配额令牌桶 + 凭证代持 + 键前缀加租户命名空间。
  @frame: 9601fdf9-2fa0-4a9f-90ae-c56819ffc692
- 「可测试可复现」在你们单测里到底怎么兑现的？图拓扑怎么单测？
  三层：节点级用录制回放（真实模型响应做 fixture），固定输入比结构化输出；图级用假节点（可编程判断结果）验证路由与收敛路径，含不收敛截断分支；端到端用 mock LLM 跑全图比对报告骨架。可复现靠确定性路由 + 状态快照，不在单测里调真模型。
  @frame: 8cf569e4-5f2a-4b77-b9ce-a1c495cd7635
- 提示词版本化后，效果回归怎么做？旧版本模板还需要维护吗？
  回归集 = 固定主题集 + 关键指标（收敛轮数/引用准确率/格式失败率）版本化对比；灰度期新旧双跑，指标不达标即回滚标签；废弃版本只留标签不再维护，模板仓目录按角色分层避免根目录膨胀。
  @frame: 7549210c-25f1-424d-bb78-1bf7ada944b6
- 多 Agent 系统中错误传播和单模型有什么不同？你们的爆炸半径控制做了什么？
  单模型错误只影响输出，多 Agent 上游错误会被下游当真话放大（Keyword 跑偏→Summary 白读→Report 自信地写错）。控制：每节点结构化契约校验入口、单点失败降级不中断、置信度与过程记录把不确定性透传给用户。
  @frame: 3450e0aa-5a5d-46a8-bcd7-32b43a617fb6
- 这个系统和你的政务 RAG 项目方法论上有哪些共通沉淀？
  三条可复用方法论：结构化输出自约束（RAG 的生成约束 / 本项目的 Agent 契约）；可解释溯源闭环（RAG 的页码图表链路 / 本项目的来源 ID 校验）；确定性评估优先于模型自评（RAGAS 回归 / 置信度公式）。两个项目互相验证了同一套工程主张。
  @frame: 775497d4-7194-49c5-803a-63c88c17ea60
- 面试官追问：你说控制流确定性，那模型输出本身不确定，这个矛盾怎么自洽？
  不矛盾：不确定性被隔离在节点内的语言生成，出口处用结构化 schema 强制收口——模型决定「说什么」，代码决定「走哪条边」；判断结果空间穷举且可测，所以图上控制流确定，生成内容另用置信度与抽检度量。
  @frame: d86dc3ee-c388-42bb-8a63-2dbb9d3790c6
- 长任务的用户体验：8-15 分钟等待里用户应该看到什么？你们怎么设计的？
  逐轮进度流：当前轮次/角色、新来源标题、Judge 缺口判断（为什么还要查）草稿预览。过程透明同时解决体验与信任：等待可接受性来自看得见在干活，也来自终稿可审计——过程数据和审计数据同源复用。
  @frame: ee5a6a74-5edd-4a4a-afde-d551c5e2c0c8
- 领导质疑：这不就是调 LangChain 几个 API，核心竞争力在哪？你怎么回？
  框架只给机制，质量在策略：四角色分工与判据设计、双层收敛保险、引用程序校验、确定性置信度、会话隔离与成本熔断都是自研决策；反证是把这几个机制从代码里抽走，系统退化成不可审计的玩具 demo，无法上政务生产。
  @frame: 3f0771d6-fcea-4eff-be5b-423e87ab361e
- 你们没有在线学习闭环——报告被人工纠错后，系统会变得更聪明吗？应该怎么设这个闭环？
  不会，目前纠错只回流到模板判据的人工迭代。设计上不碰模型权重：纠错标注沉淀为 Judge 判据示例库与检索源黑名单，模板灰度接入；闭环风险是反馈污染主链路，所以只进评估数据不进运行时状态。
  @frame: 57c765f3-fbc9-4945-a6af-c1a6b659e26b
- 用架构师视角重新审视：这个系统真正的技术难点是哪一个，其他都是工程套话吗？
  真难点是「让不确定的生成器产出可审计的结论」：编排/隔离/模板都是成熟工程；难在质量策略设计——什么信号能信（确定性指标）、什么必须拦（引用校验）、什么要透传（置信度降级），这套判断才是别人复现不了的壁垒。
  @frame: 167921d5-f940-43f8-a40e-0a80e5620f76
- 如果 Judge 的判据和确定性指标矛盾了（模型说充分、缺口覆盖率只 60%），听谁的？为什么？
  听确定性指标：缺口未覆盖是硬事实，模型判充分可能是被貌似完整的笔记误导——这是它偷懒模式的一部分；但不一刀切否决，冲突信号记入审计事件，累积后反哺判据迭代，让模型判断受数据监督而不是被数据替代。
  @frame: c0f1d6d7-ceab-4d1b-9f2d-64bcb4c54b02
- 把这个系统讲给不懂 AI 的业务方负责人听，你怎么在 3 分钟内让他决定试点？
  不谈 Agent 谈风险：以前人写调研报告三小时且查无可据；现在十五分钟出稿，每句结论能点开原文、来源不够会标明存疑、全程有记录可回放——审计需求恰好是人工模式最难满足的。试点只限一个场景：内部研究参考，对外发布仍需人工签发。
  @frame: 6b068286-d208-449b-abbd-91b5b19f3b9d
- 设计一个防投毒场景：调研对象是竞品发布的恶意构造网页，你的链路哪些点会被利用？
  两个利用面：Summary 把注入指令当真话写进笔记，再进 Report 形成结论（提示注入随内容进上下文）；来源时效分布可能被批量伪新页面拉高置信度。缓解：不可信源内容作数据不作指令、来源域名信誉分级、关键结论交叉印证要求多源。
  @frame: b10d0038-ef38-4dfe-8580-2b3395f6f983
- 单 Agent + 工具（如一个带搜索的 ReAct）就能覆盖大部分能力，你的四角色结构是不是过度设计？什么时候该降级成单 Agent？
  不是：单 ReAct 的控制流由模型决定，游走漂移难复现、过程难审计，而政务场景要的是可回放可归因；降级条件：任务短（一两步完成）、无审计要求、允许失败重跑——三个条件都满足时单 Agent 确实更便宜，选型该跟着任务形状走。
  @frame: ef9bbdc8-4712-4d9a-8a7a-d27a09d5f211
- 你如何向团队论证 LangGraph 的选择是对的？如果某天要迁移走，成本怎么控？
  论证用需求映射：回环收敛→条件边、断点→Checkpointer、审计→状态快照，三个硬需求都是库内能力而不是自己拼。迁移成本靠隔离层控：节点只依赖状态 schema 不依赖库对象，checkpoint 后端数据导出自有格式，换框架重写的只是图编译那一层。

## 项目亮点挖掘

1. **状态机编排可控可测**
   LangGraph 有向图编排四角色 Agent，控制流确定性、可测试、可复现，语言任务完全下沉至 Agent 节点。
2. **断点续跑与过程可审计**
   Checkpointer 状态持久化 + on_progress 回调逐轮落盘，研究过程可回放、可断点恢复。
3. **迭代收敛机制**
   Judge 判断信息充分性驱动多轮补检，max_rounds 保证收敛，单点失败不拖垮全局。
4. **结构化输出工程**
   Pydantic 自约束把格式解析失败率压至 0.1% 以下；来源按 URL 去重、置信度确定性计算。
5. **会话级多租户隔离**
   FastAPI + Redis 实现多用户 session 上下文隔离与动态内存管理，高并发下零污染。
6. **提示词资产化**
   Jinja2 模块化模板管理 5 类 Agent 提示词，版本化、热更新、与控制流解耦。
