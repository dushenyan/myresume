## 预测押题

- Agent Skills 的本质是什么？和直接在系统提示词里写指令有什么区别？
  本质是渐进式披露的外部能力文档：平时只占名称+描述的索引额度，任务命中才加载正文。系统提示词是全量常驻，Skills 按需加载，同样能力覆盖下上下文成本低一个量级。
- 你说「只写代理需要的能力、剔除模型已知常识」，怎么判断一条知识该不该进 Skill？上下文占用怎么控制？
  判断标准：模型反复做错的、我有稳定偏好的、项目特有约定才写；通用常识模型已会，写了是噪声。控制靠分层（只有一级常驻）+ 正文精简 + 大段参考拆成按需文件。
- AGENTS.md 驱动技能生成流程是怎么运作的？人和 Agent 各负责什么？
  AGENTS.md 是「写技能的技能」：规定结构、分层、语气、裁剪标准；Agent 按元文档生成/重构具体技能，人负责评审触发描述与取舍。规范集中一份，改规范即改全部后续产出。
- core / features / best-practices / advanced 四级组织解决什么问题？
  解决「全量加载太贵、随机抽取太乱」：core 是高频主干，features 按场景命中，best-practices 约束质量，advanced 低频才取——加载优先级与成本分层一一对应。
- 三源维护架构：手写、官方文档生成（submodule）、vendor 第三方，三类来源的更新策略分别是什么？怎么防止上游文档变化导致技能失效？
  手写按使用反馈事件驱动改；submodule 直引官方仓库，更新 = bump submodule 指针，内容永远随上游走；vendor 定期同步 + diff 评审。防失效：官方源天然不过期，手写技能定期用任务集验证触发是否仍准确。
- 自动检测 20+ AI 编辑器的技能目录是怎么实现的？各家目录约定不同怎么兼容？
  表驱动：内置已知客户端的配置表（特征文件/目录路径/技能格式），启动时探测存在性命中即为目标；新客户端加一行表项而非改逻辑，也支持用户自定义目录兼容未收录工具。
- 为什么用软链接全量对齐而不是复制？删除清理要保证什么一致性？
  软链接单一事实源，仓库更新全部客户端立即生效；复制会版本漂移还要 N 处同步。删除清理指仓库里删掉的技能，同步时检测失效链接并移除，保证各端与仓库集合完全一致无残留。
- --dry-run 在分发 CLI 里防什么事故？--uninstall 怎么做到不残留？
  防批量链接/删除操作误伤用户自建内容：先打印将执行的完整动作清单。uninstall 只移除清单内由本工具创建的链接（安装时记录 manifest），用户自有文件不碰，移除后再校验一致性。
- 技能在多个 Agent 客户端间「一致」为什么重要？不一致会带来什么体验问题？
  日常工作流横跨多个客户端，能力不一致会出现「这个工具会那个工具不会」的不可预期行为，同一规范下产出风格漂移，排查成本极高；一致性是资产化的前提。
- 这套体系怎么支撑你简历里「沉淀 Skills/Rules 约束 AI 产出」的主张？工作项目里怎么用的？
  工作中把团队代码规范、文档模板、诊断流程写成技能/规则注入 AI 工作流，约束产出风格与质量门槛；本仓库就是这套方法论的生产工具与资产库，方法论和落地互相印证。

## 项目亮点挖掘

1. **技能设计规范**
   AGENTS.md 驱动生成流程，四级组织（core/features/best-practices/advanced），以上下文占用为第一约束。
2. **三源维护架构**
   手写偏好 + submodule 直引官方文档 + vendor 第三方同步，分策略维护保证技能新鲜度。
3. **跨客户端分发 CLI**
   自动检测 20+ AI 编辑器/CLI 技能目录，软链接全量对齐 + 删除清理，多工具间技能一致。
4. **细粒度控制**
   --target / --skill / --dry-run / --uninstall 完整控制面，分发可模拟、可回退。
5. **上下文工程资产化**
   把日常 AI 工作流的偏好沉淀为可版本化、可分发的技能资产，与工作履历互相印证。
