## 预测押题

- 告警风暴如何去重？去重策略怎么设计，如何避免漏掉真实的新故障？
  分级去重：指纹（告警源+指标+标签）完全相同短窗口内折叠计数；同服务相关指标归并成事件。防漏：新指纹、阈值跳变、持续时长超限三类信号强制新开事件，去重只折叠不吞告警，原始告警全部落库可回溯。
- 多条告警同时到达，如何判断它们是同一个根因（告警关联/聚合）？
  三维关联：时间窗口接近 + 拓扑/服务依赖关系相邻 + 症状类型互补（接口慢+连接池满+CPU高），命中两条以上归并为同一诊断上下文；没有拓扑数据时降级为时间+文本相似度聚类，并标记关联置信度供人工复核。
- 关键指标如何筛选？为什么不把全部日志/指标直接喂给 LLM？
  规则引擎按告警类型选指标集（错误率/延迟/资源/依赖四模板）+ 异常检测只保留偏离基线的时段。全量喂入三个问题：超出上下文窗口、成本爆炸、噪声降低推理质量——取证是诊断质量的第一瓶颈，筛选本身就是能力。
- ReAct"观察-假设-验证"循环具体怎么落地？如何防止循环失控或取证跑偏？
  每轮把已收集证据+候选根因注入 prompt，模型输出下一步取证动作（查什么日志/指标）或下结论；工具层执行后回填观察。防失控：最大轮数硬上限、同一查询去重拦截（防反复查同一处）、每轮假设必须引用已有证据，无新证据支持则强制收敛。
- 历史故障案例库如何构建与召回？冷启动阶段没有案例怎么办？
  每次诊断结束（人工确认根因后）将「症状特征-证据链-根因-处置」结构化入库，新告警按症状相似度向量召回 top-k 案例作为先验提示。冷启动：先用 Runbook/复盘文档人工构造种子案例，同时把每次真实诊断都变成增量语料，准确率随案例积累爬坡。
- LLM 的根因结论可能幻觉，你用什么机制保证结论有证据支撑？
  结论结构化约束：根因必须附带证据引用（具体日志行/指标时间序列 id），后端逐条校验引用真实存在于本次取证结果，引用不成立的结论自动驳回重进循环；呈现时证据与结论同屏，人可秒验。
- 根因准确率如何评估？评估集怎么来、打分标准是什么、如何持续提升？
  用历史故障复盘构建评估集（告警输入+人工确认的真实根因），回放跑诊断，根因命中即得分（92/100 这么来的）；部分分给「方向对但层次错」。提升：错例归因到取证不足/案例误导/提示词缺陷三类，分别补指标模板、修案例、调 prompt，改完全量回归防倒退。
- 为什么高危操作要 HITL 人工确认？如何平衡"自动化提效"与"变更安全"？
  诊断可以错但不能致命：重启/扩容/回滚等变更操作影响生产，模型误判的代价大于人工确认的几分钟成本。分级平衡：只读取证全自动，低风险预案（清缓存）可配置自动，高危必人工带风险提示——自动化边界按可逆性划，不按能力划。
- 修复执行失败了怎么办？回滚机制如何设计？
  执行前拍验证基线（目标指标），执行后短时窗口比对：未恢复或恶化即中止后续预案，触发回滚（预案成对定义 forward/rollback 动作，如扩容↔缩容、重启↔恢复旧副本），回滚失败升级人工告警。全程审计流水可回放。
- 如何对接真实监控栈（Prometheus/ELK/K8s）？证据源扩展时诊断层为什么零改动？
  证据源定义为统一接口（query_metrics/search_logs/get_events），Prometheus/ELK/K8s 各写适配器实现，接口预留 mock 实现先行验证链路。诊断层只面向接口编排取证动作，新接一个数据源 = 新增一个适配器，ReAct 循环与结论层代码不动。

## 项目亮点挖掘

1. **ReAct 诊断循环**
   观察（规则引擎筛选关键指标）→ 假设（案例库召回 + LLM）→ 验证（LLM 调度工具取证，上限 3 轮）→ 结论，实测定位到具体变更 deploy-v-2.3.1。
2. **告警风暴防护**
   P1-P3 分级 + 300s 窗口去重 + 按服务聚合，4 条告警收敛为 1 次诊断，避免重复取证与告警疲劳。
3. **关键指标筛选规则引擎**
   4 条阈值规则从海量证据中过滤噪声，只把异常信号喂给 LLM，降低 token 成本与幻觉面。
4. **HITL 安全处置**
   修复方案先经 LLM 风险评估，高危操作无确认一律拦截，执行失败自动回滚，演示中阶段一拦截、阶段二确认后执行成功。
5. **根因准确率评估**
   诊断结论与事后标注根因对比打分，≥80 记命中，实测 92/100，支撑诊断质量可量化回归。
6. **证据源零耦合**
   替换 MockCollector 即可对接 Prometheus/ELK/K8s API/CMDB，全链路离线可跑。
