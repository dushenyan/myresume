- 向量数据库到底是干什么的？为什么做 RAG 离不开它？
  它是存「语义向量」并提供「按相似度找最近邻」的专用存储。RAG 要「根据问题的意思找回相关文档」，靠字面匹配做不到，得先把文本编码成向量存进库，查询时把问题也编码成向量、去库里找最近的若干条。它真正解决的是高维向量的快速近似最近邻搜索（ANN，Approximate Nearest Neighbor）——普通数据库在百万上千万向量下扫全表扛不住，向量库用 HNSW / IVF 这类索引把「逐个比」变成「跳着比」。一句话：向量库 = 为「按意思找」这件事专门优化的检索引擎。
- embedding 模型和向量库是什么关系？分工怎么切？
  两个东西、一条链：embedding 模型负责「翻译」，把一段文本变成一串定长数字（向量），语义越近的文本向量越靠近；向量库负责「收纳 + 查找」，把向量连同原文和元数据存起来，支持「给一个查询向量，返回最像的 top-k」。也就是 文本 →(embedding)→ 向量 →(向量库)→ 相似检索。关键边界：向量库只认「维度」和「距离」，它自己不产生向量，所以用哪个模型、输出多少维、配什么度量，都是你在 embedding 侧定好后喂给它的。模型一换，旧向量全部作废必须重刷——这是两者最容易被忽略的分界线。

- Chroma 是怎么用的？数据到底存在哪儿，「嵌入式」意味着什么？
  嵌入式 = 它就是个跑在你进程里的库，没有独立服务器。pip install 完，指定一个本地目录 persist_directory，Collection（集合，相当于向量表）就落在这个目录的文件里，读写都是函数调用，不用起服务、不用连端口、没有连接池。基本用法是建 Collection → add 文本和向量 → query 查询向量拿 top-k，它还自带一个默认 embedding 函数，三行就能跑通。定位类比 SQLite：单文件、零运维、适合原型和中小数据。代价是它不是分布式服务，多机共享、高并发、水平扩容不是它的主场，生产大流量通常换成 ES 或专用向量库。
- Elasticsearch 不是全文搜索引擎吗，它怎么就支持向量检索了？
  ES 7.x 起加了 dense_vector 字段类型（专门存稠密向量的字段），8.x 又把它和顶层 knn 查询、knn_vector 索引打通，于是 ES 变成「全文 + 向量」双模引擎。你把 embedding 出来的向量写进某个文档的 dense_vector 字段，ES 内部给这个字段建 HNSW 图；查询时发一个 knn 请求，带上查询向量、目标字段、k 和 num_candidates（候选池宽度），ES 就走这张图返回相似结果。它最大的卖点是「顺带」：你本来就用 ES 做日志和全文，现在同一条 query 里既能 match 字面又能 knn 语义，一次请求双路召回，不用为向量单独起一套系统。

- 简历写「Chroma / Elasticsearch 向量库双栈」，为什么要两个向量库？一个不够吗？
  @answer: chroma-es-dual-vector-stack.md
- 市面上 Milvus / FAISS / pgvector 都能做向量检索，你为什么偏偏选 Chroma + ES 这一对？选型按什么标准走？
  先给各家定位：FAISS 是近邻计算「库」不是「服务」，没有增删改和持久化，用它是为了自己造向量库；pgvector 是给 Postgres 加的扩展，杀手级好处是「业务数据和向量同库同事务」，百万级以下、本来就跑 PG 的团队最省事；Milvus 是分布式专用向量库，亿级向量、GPU 建索引、高并发才划算，代价是依赖链很重（消息队列 + 对象存储 + 多角色节点）；Chroma 是嵌入式向量数据库，pip 装完即用，原型首选；ES 是全文引擎顺带做向量，胜在你已经在用它、能一次请求做 BM25 + 向量双路。我落在这对上是因为需求刚好卡在中段——数据量千万级以下不需要 Milvus，但要做语义 + 字面混合检索、且生产已有 ES 集群，所以开发期 Chroma 起步、生产期 ES 收口。选型我只问三句话：数据多大？要不要跟别的数据同库？团队养不养得起一套分布式系统。
- 向量相似度该选余弦、内积还是 L2？配 bge 这类中文模型有讲究吗，为什么大家都先做归一化？
  bge 系列官方推荐余弦相似度（它训练时就是把语义相近的文本在方向上拉近）。三种度量的区别：余弦只看方向、内积看方向也看向量长度、L2 看直线距离。关键一点——如果向量都归一化成单位长度（模长为 1），余弦、内积、L2 会给出完全一致的排序，选哪个都不影响结果，只是数值范围不同。所以标准做法是 embedding 出来先归一化，再统一按「越大越相似」处理（ES 的 dense_vector 可显式配 similarity: cosine，Chroma 默认 L2 但换 cosine 度量后分数是 1−cos 越小越像）。不归一化直接上内积/L2，模长大的文档会白占便宜，排序就歪了。

- ES 里 dense_vector 的 knn 查询，和用 script_score 现场算余弦，有什么本质区别？什么时候该用后者？
  knn 走 HNSW 近似最近邻（靠牺牲一点精确度换几个数量级的速度），快但结果近似、理论上会漏真正的 top-k；script_score 是把查询向量和每个候选文档逐条现算相似度，精确 100% 但要扫全部文档、慢且吃 CPU。所以默认用 knn；只有两种场景才上 script_score——数据小到几千几万条（暴力算都秒回，没必要近似），或者你要拿它当「标准答案」去测 knn 的召回率够不够。
- HNSW 的 M、ef_construction、num_candidates 这几个参数你会怎么调？各自的代价是什么？
  分两类：M 和 ef_construction 是「建索引时」定死的——M 是每个节点连的边数，越大图越密、召回越高但索引更大建得更慢；ef_construction 是插入新元素时搜索的候选宽度，越大建出来的图越准、建索引越慢，这俩影响的是索引质量，调好就得重建。num_candidates 是「查询时」的候选池宽度（对应 HNSW 的 ef），是唯一能在线调的旋钮，调大→更准但更慢。我的经验是 num_candidates 从 k 的 5～10 倍起步，用抽样 query 看召回够不够再加，绝不一上来拉满——那是拿延迟换一个你已经够用的召回率。
- 文档新增、修改、删除时向量库怎么跟着变？什么情况走增量，什么情况必须全量重建？
  我按变更性质切：内容级变更（改几条文档、上下架某篇）走增量——ES 是近实时，写完默认约 1 秒可搜，增删改原生支持；Chroma 也有 add / update / delete，但它是嵌入式文件存储，高频写或大改集合会掉性能，所以更该把它当「可重建的缓存」，权威数据放上游数据库。表示级变更（换 embedding 模型、改向量维度、重切分块规则）必须全量重刷——因为不同模型的向量空间互不相通，新旧向量混在同一个集合里检索必然串味，只能新建集合或清空重建。一句话标尺：改内容走增量，改「怎么表示」走全量。

- 带元数据过滤的检索（metadata filtering）你会怎么做？为什么「先过滤再做 ANN」有时反而更慢、召回还下降？
  这类需求来自多租户 / 权限 / 分类召回——只在某个子集里做相似检索。两种实现：pre-filter 先按条件筛出候选再在候选里跑 ANN，post-filter 先 ANN 拿 top-k 再按条件丢弃。坑在于 HNSW 是在整张图上「跳着走」找近邻，pre-filter 时大量节点被标成不可访问、图的连通性被打断，贪心走图可能提前卡住导致召回下降；post-filter 更糟，top-k 过滤完可能所剩无几，你以为是没相关内容其实是被砍光。所以现代向量库（ES 8.x 的 filtered knn、Milvus）走「把过滤条件带进图遍历」或扩大候选池来补偿。经验：当过滤选择性很强（剩下的本来就少），别硬用 ANN，退化成对过滤后小集合跑 brute-force（script_score）反而又快又准。
- 从 Chroma 切到 ES，LangChain 那层有哪些「接口看着一样、其实不一样」的坑？
  三个最容易踩的。一是分数方向：similarity_search_with_score 在 Chroma 返回的是距离（越小越像），在 ES 返回的是相似度（越大越像），直接透传给下游排序会整个反掉，必须统一归一到「越大越好」再比较。二是过滤语法：Chroma 用 where={...}，ES 用查询 DSL，LangChain 封装了一部分，但稍微复杂的元数据过滤还得各写各的，切换时这层要重写。三是高级检索会静默降级：as_retriever 的 search_type（比如做多样性的 mmr）不是每家后端都支持，切过去可能悄悄退回普通 similarity 而不报错。所以迁移后我一定拿固定 query 集把 top-k 和分数逐条比对，就是专门为了把这几处差异逼出来。
- 数据涨到亿级、单机扛不住时，向量检索这条链上你会先动哪个旋钮？
  按性价比顺序动，不是一上来就分布式。先调索引和量化：HNSW 换 IVF-PQ（倒排 + 乘积量化，牺牲一点召回换内存和速度），或给向量做标量量化（float32 → int8，内存直接砍一半以上）；再上分片（sharding）把集合切到多机并行；最后才考虑 GPU 建索引或专用向量集群。同时回头砍需求——真需要全库检索吗，能不能先按业务维度（租户 / 时间 / 类目）分区，每个分区各自 ANN，分区既降规模又天然带隔离。诚实边界：我实操的项目在千万级以下，没真跑过亿级线上，这题答的是「知道链条上每个旋钮往哪拧、代价是什么」，被追细节我会引到 IVF 聚类中心、PQ 子空间编码这些原理讲清，但不编没做过的压测数字。

## 项目亮点挖掘

1. **基础概念闭环**能讲清 embedding 与向量库的分工边界（模型一换旧向量全废）、Chroma「嵌入式 = 进程内库」的定位与天花板、ES 靠 dense_vector + knn 从全文引擎长出的向量能力
2. **双栈认知**不止会换 VectorStore 类，讲得清「嵌入换壳不换」：Chroma 与 ES 8.x knn 底层同为 HNSW，差异在工程壳（部署形态、配套能力、运维归属）
3. **抽象层落地**：LangChain VectorStore 接口下检索链路零改动切换底层向量库，验证方法论为「embedding 模型冻结 + 抽样 top-k 一致性比对」
4. **底层参数与度量两手硬**：讲得清 HNSW 的 M / ef_construction（建索引质量）与 num_candidates（在线召回↔延迟）分工，以及 embedding 归一化后余弦/内积/L2 排序等价的原理
5. **增量 vs 全量重建有判断标尺**：内容级变更走增量（ES 近实时 / Chroma upsert），表示级变更（换模型 / 改维度 / 重切块）必然全量重刷，杜绝新旧向量混存串味
6. **过滤检索与规模化有边界感**：讲得清 metadata 过滤打断 HNSW 图连通性导致召回下降、高选择性时退化 brute-force，亿级才动 IVF-PQ / 量化 / 分片，且不臆造没压测过的线上数字
