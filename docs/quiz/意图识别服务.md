## 预测押题

- 规则、TF-IDF、BERT 微调、动态 Few-shot LLM 四方案各自的适用边界是什么？你是怎么设计对比实验的？
  规则：零标注数据、高频明确表达；TF-IDF：百级样本、表达稳定；BERT 微调：千级样本 + 低延迟高准确要求；Few-shot LLM：长尾语义冷启动但延迟成本高。对比实验：同一评估集、统一指标（准确率/P99/单次成本/最低数据量）四后端同接口跑分。
- 选型评估用了哪些指标？除了准确率，成本、延迟、冷启动数据量怎么纳入决策？
  准确率/分类 F1 + P99 延迟 + 单次调用成本 + 冷启动标注量构成决策矩阵：新意图冷启动用 LLM，验证有量后换 BERT 降成本，高频确定性表达用规则兜底，按阶段递进而非一步到位。
- BERT 微调准确率 95%+ 的数据集多大？训练集怎么构建的，类别不均衡怎么处理？
  每意图百级标注（真实语料 + 改写增强）共千级样本；不均衡用类别权重损失 + 少数类过采样，评估看分类 F1 而非总体 accuracy，避免大类掩盖小类。
- 推理 P99 < 50ms 怎么测的？模型做了什么优化（量化 / 批处理 / 蒸馏）？
  压测脚本固定并发统计分位延迟。优化：max_length 截断避免长序列浪费、推理批处理聚合窗口、小参数量模型选型（中文 small 级 BERT），必要时 INT8 量化。
- 动态 Few-shot 的示例是怎么挑选的？和固定 Few-shot 比优势在哪？
  用历史标注样本建向量索引，按输入检索 top-k 相似样本拼进 prompt。优势：长尾意图能被相近样本带到，固定示例永远覆盖不到的类别也有机会判对；代价是检索一跳延迟。
- TF-IDF + 传统分类器方案在什么数据规模下就不够用了？你观察到的瓶颈是什么？
  样本加到几千条后准确率增益明显递减，瓶颈是词袋表达不了同义改写和歧义（「办不了」vs「办不了理」），需要成倍新数据才能维持提升，这时换 BERT 性价比反超。
- 意图体系怎么定义的？新增意图类别时四方案分别要付出什么改动成本？
  按客服路由目标划分意图类目（与业务方对齐）。新增类别：规则加词条当天可上；TF-IDF 补数据重训；BERT 补数据微调且有灾难遗忘风险需全量回归；LLM 只改候选集+示例，成本最低——这正是递进选型的依据。
- 分类错误在客服场景的代价是什么？置信度低的样本你怎么处理（转人工 / 追问澄清）？
  错路由让用户体验受损且消耗人工二次处理时长。低置信度样本不硬猜：走追问澄清或直接转人工，阈值按「错判成本 vs 澄清成本」的代价曲线标定。
- 为什么把模型推理统一集成到 FastAPI？同步调用和异步批处理怎么权衡？
  四方案统一接口才能公平对比，业务侧切换后端零改动。单条低延迟请求走同步；高吞吐场景用异步 + 短聚合窗口攒批推理，延迟预算内换 GPU/CPU 利用率。
- 这个项目对你后续做 RAG / Agent 的影响是什么？为什么说它是「选型起步」？
  它建立了「先建评估集、量化对比再选型」的工程习惯——后来 FAQ 中台的融合检索调参、RAG 的 RAGAS 回归、Agent 的 LangGraph vs ReAct 取舍都是同一方法论的延伸。

## 项目亮点挖掘

1. **四方案横向对比**
   规则 / TF-IDF / BERT 微调 / 动态 Few-shot LLM 同数据集对比压测，形成按成本与语义复杂度的递进选型方法论。
2. **BERT 微调落地**
   微调方案准确率 95%+、推理 P99 < 50ms，验证了小样本意图分类上微调模型的性价比。
3. **动态 Few-shot 实践**
   按输入动态检索示例拼装 Prompt，对比固定示例在长尾意图上的召回差异。
4. **统一服务化**
   模型推理统一集成 FastAPI，四方案共享同一评估与压测管线，结论可复现。
5. **AI 主线起点**
   2024 年选型起步实践，为后续 FAQ 中台、GraphRAG、Agent 项目奠定评估驱动的工程习惯。
