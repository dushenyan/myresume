## 预测押题

<!-- 第一梯队：入门（1-12）基础概念与背景热身 -->

- 用一分钟介绍一下这个项目：它是干什么的，服务谁，包含哪几大能力？
  @frame: b79e22f9-4f69-48cf-b3fa-e81e3ead491c
- 为什么 FAQ 场景既要 BM25 全文检索又要向量语义检索？只用一种行不行？
  @frame: 35de0958-6bfc-41ea-92ce-1e3127ab169b
- BM25 是怎么给文档打分的？为什么搜专有名词、证件编号它特别准？
  @answer: bm25-scoring.md
- 向量语义检索为什么能搜到“字面不一样、意思相近”的内容？
  @answer: vector-semantic-search.md
- Elasticsearch 8.x 在这里承担什么角色？dense_vector 字段是干什么的？
  ES 一个系统同时承担全文与向量两路检索：普通字段走 BM25，dense_vector 字段存 FAQ 的语义向量并建近邻索引，查询时用 knn 检索相似向量。单引擎双路让融合可以在一次请求里完成，不用跨系统拼数据。
- BM25 分数和向量余弦分数量纲不同，为什么这会影响融合策略的选择？
  BM25 分数无上界、余弦分数固定在 0~1，直接加权求和等于让一个永远占优的量纲绑架另一个，归一化又对分数分布敏感很脆弱。所以才需要 RRF 这种"只看排名不看见分"的融合方式绕开不可比问题。
- Script Score 加权和 RRF 两种融合方式区别在哪？你们什么场景用哪个？
  Script Score 是对两路分数做表达式加权，要求分数可比、需归一化，适合业务明确要调权重时；RRF 只用各路内的排名算总分，免归一化、鲁棒性好。实践是 RRF 为默认，需要显式调权且分布稳定时才上 Script Score。
- P99 < 200ms 这个指标什么含义？为什么不承诺平均值而是 P99？
  P99 是 99% 的请求都快于 200ms。平均值会被少量极端慢请求掩盖（平均 100ms 但 10% 的人等了 5 秒），客服场景要保的是"几乎所有人都快"，所以用高分位数承诺。
- P99 < 200ms 是怎么测出来的？链路里最慢的是哪一段？
  压测工具按真实查询分布混合打流量，统计端到端（收到问题到返回 Top-K）的分位延迟。最慢的一段是查询向量的 embedding 推理，优化手段就是本地常驻模型加批量推理，把网络往返砍掉。
- Top-5 命中率 92% 是什么口径？标注集怎么来的？
  用真实高频政务问题构造标注集，人工判定返回的前 5 条里是否包含能回答该问题的知识，命中比例即 Top-5 命中率。样本覆盖多渠道真实查询，不是挑简单题测的。
- 向量推理为什么选 Sentence-Transformers 本地化部署而不调远程 embedding API？
  三个理由：远程 API 每次调用多一跳网络往返，200ms 预算直接被吃掉一大块；查询向量是检索的前置依赖，远程调用等于把整条链路可用性绑到外部服务；政务场景对数据出域敏感，本地推理天然合规。
- 单索引单分片在你们场景下为什么反而是性能优化？
  5 万级条目体量小，单分片把所有数据放在一个执行单元里，查询不走"各分片局部排序再全局归并"的跨分片协调路径，分数无需归并、路由无需分发，延迟更低且结果稳定。分片多寡对性能是有成本的，小数据量上拆分片纯交学费。

<!-- 第二梯队：中级（13-26）五大板块机制讲清 -->

- 完整讲一遍融合检索链路：一个用户问题进来后发生了什么？
  请求进来先查搜索结果缓存，未命中则把问题过本地 Sentence-Transformers 算查询向量，一次 ES 请求同时发起 BM25 与 dense_vector knn 两路召回，RRF（或调权场景下的 Script Score）融合排名取 Top-K，组装多视角答案后回写缓存返回。
- ES 8.x 的 RRF 是引擎原生能力还是要自己写？融合发生在哪一层？
  ES 8.x 提供了检索层的 reciprocal rank fusion 能力，两路子查询的排名融合可以直接在引擎内完成；对融合逻辑有更深定制（按渠道调权、结果级过滤）时用 Script Score 把控制权收回应用层，两种都保留是刻意的。
- 查询向量一次请求要算几次 embedding？候选 FAQ 的向量什么时候算？
  查询向量每次请求算一条（本地推理毫秒级）；FAQ 侧向量在知识写入/更新时算好落进 dense_vector 字段，检索时只做近邻比较——写时重算、读时轻查是向量检索的常规分工。
- 双路召回各取多少条、融合后取 Top 几，这个怎么定？
  两路各取一个比 Top-K 明显大的候选集（太窄会在融合前就漏掉"单路第二名片"），融合后按产品要求取 Top-5 下发。候选集宽度是压过延迟的：太宽 Script Score 阶段开销上升，200ms 预算下取了平衡点。
- Sentence-Transformers 具体用的什么量级的模型？效果和延迟怎么权衡？
  选的是中文语义质量够用的小体量模型（几百 MB 级），CPU 上单条查询推理毫秒级；换更大模型对 Top-5 命中率增益有限，但推理延迟和资源占用翻倍，客服场景这笔账不划算。
- FAQ 新增或修改后，索引和向量怎么更新？坐席多久能搜到新知识？
  知识保存时同步重算该条向量、更新 ES 文档，向量只随内容变更重算；用户侧还能搜到旧答案的窗口由缓存 TTL 和主动失效决定——写路径同步失效相关 key，正常情况秒级生效。
- 7 类缓存是按什么维度划分的？为什么不是一层"查询结果缓存"打天下？
  按数据的访问特征分：类目树、导航目录、渠道配置这类结构数据稳定高频，给长 TTL；FAQ 详情、答案视角随内容变更，绑定失效策略；搜索结果和热门 FAQ 高频易变，给短 TTL。一层通用缓存必然在"新鲜度"和"命中率"上互相打架。
- 差异化 TTL（5 分钟～24 小时）具体是怎么定出来的？
  按每类缓存"变更后容忍多久的旧数据"倒推上限，再按命中率正向调到可接受区间：配置类一天改不了几次给 24 小时；搜索结果随时可能因知识发布而变化，但有主动失效兜底、TTL 只作安全网，给 5～15 分钟。
- 缓存装饰器怎么实现的？为什么说"统一收口"很重要？
  基于 functools 装饰器包住 service 层读函数：自动生成 key（类型 + 业务标识 + 参数摘要）、读穿透回源、统一记录命中埋点。收口的价值在于缓存策略变更（换 TTL 规则、加失效钩子）只动一处，不散落在几十个业务函数里。
- 搜索结果缓存的 key 怎么设计？同样的问题不同渠道算不算同一个 key？
  key 由规范化后的查询文本 + 渠道 + 分页参数构成：文本做去空格、全半角归一，避免同查询不同写法击穿；渠道必须参与 key，因为同一问题不同渠道返回的形态不同，跨渠道共享反而会串答案。
- 写操作主动失效和 TTL 过期，谁主谁次？为什么两个都要？
  主动失效是主——精确、及时，解决"改了就要立刻对"；TTL 是安全网——兜住失效动作遗漏、异常中断的场景。只有 TTL 会有窗口期旧数据，只有主动失效则一次漏发就永远脏，两条腿缺一不可。
- 双环境发布里 env 字段隔离怎么工作？为什么不用两张表或两个索引？
  同一张表存测试态与正式态两套记录，查询入口按 env 过滤。同表是因为两类记录结构完全一致、发布本质是"跨 env 同步内容"，拆表会让模型和同步代码翻倍；独立索引则是检索层的隔离选项，业务层还没到需要索引级隔离的体量。
- original_id 溯源解决什么问题？没有它会怎样？
  正式记录通过 original_id 指回来源测试记录，解决两个问题：再次发布时能识别"这是同一条的更新"而不是插一条新的（防重复）；审计时能回答"这条线上知识是谁在测试环境验过的"。没有它，发布中心退化成只会复制粘贴的脚本。
- 渠道适配引擎抽象了什么？新增一个渠道（比如小程序）要改哪些地方？
  抽象"答案形态 × 渠道能力"的映射：知识存多视角答案，渲染层按渠道支持的形态（文本/富文本/交互卡片）选形态出稿。新增渠道只注册渠道配置、声明支持的形态集合，检索与知识层零改动。

<!-- 第三梯队：高级（27-42）原理与实现细节 -->

- BM25 里 k1 和 b 各控制什么？你们调过吗，什么场景值得调？
  k1 控制词频饱和速度，b 控制文档长度归一化强度。FAQ 标题答案普遍短小，长度差异不悬殊，默认值附近即可；真值得调的场景是文档长度分布极不均匀（政策原文混进短标题），这时 b 的影响才显著。
- dense_vector 底层用的什么近邻索引？近似最近邻的"精度换速度"体现在哪？
  ES 8.x 向量检索底层是 HNSW 这类图索引，查询用多候选（num_candidates）和搜索宽度（ef）参数控制访问的节点量：调大召回更接近精确检索但更慢。数据只有 5 万级，索引参数在默认附近就基本无精度损失。
- 精确 KNN 暴力算和 ANN 在你们数据量下怎么选？为什么？
  5 万条向量做全量暴力余弦计算在单机也只是几十毫秒级，理论上可选；仍走 ANN 是留余量：知识只增不减，且 HNSW 在十万级以上才显出优势，提前把路走宽不用二次迁移。
- RRF 公式里的常数 k（默认 60）起什么作用？改变它会影响什么？
  RRF 分数是 1/(k + 排名)，k 越大头部名次的区分度越平缓、腰部名次差距影响越小。k 调小会更迷信"两路都排第一"的强共识，调大则更接近平等投票；默认 60 是经验值，我们没有为它专门调参——融合层鲁棒就鲁棒在不敏感。
- Script Score 加权用原始分数会出什么问题？要做哪种归一化？
  BM25 无上界、余弦有界，直接相加等于让 BM25 主导排名。要做 min-max 或 z-score 归一，但归一化依赖当次结果集分布，分布一漂移权重就失真——所以加权方案只在查询分布稳定的垂直场景敢用，这是 RRF 当默认的第二重理由。
- 融合层能不能补救"两路都没召回正确答案"的查询？
  不能，融合只在已有候选里排座次，无米之炊救不了。两路都漏意味着词法语义双盲，解法在检索层之外：补同义词词典/热词运营、迭代向量模型，或把缺的知识补进库——这要分清是融合的问题还是覆盖的问题。
- 那 8% 的 Top-5 miss 主要是什么 case？有针对性改进吗？
  三类：库里根本没这条知识（覆盖问题）、全新提法向量模型没见过（模型问题）、多条件复合查询单路只解一半（拆词问题）。分别对应知识运营补漏、定期用 miss 日志微调选型候选、查询改写，命中率是被运营闭环持续顶上去的。
- 向量模型要换代（效果更好的新模型），存量向量全部失效，迁移方案怎么做？
  新旧模型向量不同空间不能混检，方案是索引级切换：建新索引带新模型前缀，后台任务全量重算 5 万条灌入，双索引并行期间读旧写新双写，验证新索引指标达标后别名一键切换，回滚就是切回旧别名。
- 缓存击穿、穿透、雪崩分别指什么？你们 7 类缓存各防了什么？
  击穿是热点 key 过期瞬间大量请求回源——搜索类热点 key 加单飞（同 key 并发只放一个回源）；穿透是不存在的查询永远击穿缓存——对空结果缓存短 TTL 占位；雪崩是大批 key 同时过期——TTL 加随机抖动打散。三类手段都收在缓存装饰器里，业务无感。
- 主动失效和并发读之间有竞态：读请求把旧值回填缓存、失效紧随其后，怎么破？
  这是经典的"回填-失效"竞态，用延迟双删缓解：写提交后先删一次，延迟小段再删一次兜住慢回填；更严谨的是 key 带版本号，写推进版本、回填带版本比对，旧版本回填直接被拒。规模不大，实际选了实现成本低的延迟双删。
- 7 类缓存的 Redis 内存怎么规划？用什么淘汰策略？
  按类型分 key 前缀统计容量，大头是搜索结果类，靠短 TTL 自然收敛；实例级用 allkeys-lru 兜底——TTL 是设计内的过期机制，LRU 是容量越界时的降级保险，两层叠加才不会被一次流量异常打爆内存。
- 缓存命中率和回源压力有埋点吗？数据反哺过什么决策？
  装饰器统一埋命中率与回源耗时。数据直接驱动过两次调整：导航目录命中率超预期于是 TTL 上调；搜索结果在发布窗口命中率骤降，据此把"发布后批量失效"从逐条改为按前缀批处理，削掉失效风暴。
- 发布过程中测试记录被同时修改、或发布到一半失败，状态怎么保证？
  发布以记录为单元做状态机流转（待发布→同步中→已生效），并发修改用版本乐观锁拦截“发布中改源”；中途失败则该记录回退待发布态、已同步的正式记录按批次回滚，发布动作设计为幂等，重试不产生重复记录。
- SSE 流式响应和 WebSocket 怎么选？打字机体验后端做了什么？
  问答是服务端单向推流，SSE 走 HTTP 语义、自动重连、鉴权与网关链路全部复用，运维成本远低于 WebSocket。后端把生成 token 流按 SSE 事件逐帧下发，并处理断线后的 Last-Event-ID 续传语义。
- 3000 条大文件异步导入怎么保证不阻塞主流程？导入一半失败了怎么处理？
  文件落盘后立即返回任务 ID，解析入库进后台异步任务分片执行；失败按批次回滚并记录行级错误清单供修正后重传，已入库批次不回滚（幂等导入按文件指纹去重），绝不产生半脏状态。
- 5 万级条目高效导出用了什么手段？SQLAlchemy 2.0 批量链路优化了什么？
  流式分批读（服务端游标 + yield_per）边读边写出，避免一次性载入内存；写侧用 bulk insert/update 绕过逐对象 unit-of-work 的开销，导入导出吞吐都上了一个量级。

<!-- 第四梯队：专家（43-54）故障场景与排障路径 -->

- 线上反馈"刚更新的知识搜出来还是旧答案"，你的排查路径是什么？
  沿数据流分段定位：先查 Redis 对应 key 是否被主动失效（失效日志有无记录）→ 再查 ES 文档更新时间与向量是否重算 → 再看是否命中搜索缓存的延迟双删窗口。顺序按"变更传播路径"倒排，每一段都有时间戳可对照。
- P99 突然从 200ms 飙到 2s，分段定位怎么做？先怀疑谁？
  先排除面性故障：缓存命中率曲线骤降意味着回源风暴，是最大嫌疑（一处失效放大全链路）；再看 ES 慢查询日志区分是检索劣化还是推理排队；embedding 本地推理的队列深度单独埋点。定位原则是先找"能解释全局变慢的单一原因"。
- 一次发布后答案口径出错，怎么在 5 分钟内止血并定位影响面？
  止血先于归因：发布中心按 original_id 反查该批次同步的正式记录，一键回滚上一版并批量失效关联缓存；影响面用发布批次号 + 查询日志圈定时间窗内命中过错误答案的会话。回滚通道必须在发布设计时就存在，不是出事前现造。
- Redis 整个挂掉，系统会怎样？降级预案做了什么？
  读路径全部穿透回源，DB 与 ES 瞬时承压，表现为延迟整体上移而非不可用——这是"降级"不是"宕机"。预案是装饰器层熔断：Redis 不可用时直接旁路、配合入口限流保护回源链路，恢复后缓存自然预热，不需要人工重建。
- ES 单节点故障对系统的影响半径是多大？
  检索直接不可用是最大冲击，这正是当初选单节点要接受的代价，缓解在两层：客服入口对"搜不到"有兜底路径（热门 FAQ 缓存与类目浏览不依赖实时检索）；演进上是加副本分片换节点级容错，数据量不需要分片但可用性需要副本。
- 有没有出现过脏数据绕过测试环境直接进了正式库？机制上怎么堵？
  设计上默认堵死：正式记录只能由发布中心从测试记录同步产生，接口层不给正式 env 直接写入口；唯一的例外通道是运维脚本，所以正式 env 字段的每次变更都进审计日志，绕过发布中心的写入可追溯可报警。
- 用户反馈"这个问题明明有知识却问不到"，排查 SOP 是什么？
  三步：拿原查询在测试环境复现，确认是检索问题还是数据问题；是检索则拆解——BM25 单跑、向量单跑、融合结果各段对比，定位是双漏还是融合排序压后；是数据则查 env 状态（是不是停在测试态没发布）和渠道形态（是不是该渠道没配这个视角）。
- 全异步链路里最怕的就是同步阻塞混入，你们踩过什么坑、怎么防？
  典型坑是在 async 路径里调了同步的 HTTP 客户端或同步 DB 会话，事件循环被单请求卡住、P99 出现无规律尖刺。防法：约定同步重活走线程池（to_thread / AsyncPG 这类真异步驱动），代码评审清单单列"事件循环阻塞"检查项，配合慢请求堆栈采样定位。
- async def 里调用一个 CPU 密集的推理函数会发生什么？正确姿势？
  事件循环被独占，其他所有协程全部等待——async 只对 I/O 等待有效，对 CPU 计算无效。姿势是把推理放进程/线程池或用 to_thread 包裹，GPU 场景再加批量聚合（攒批推理）把计算吞吐和请求延迟解耦。
- 双环境在同表，数据量等于翻倍，索引和查询怎么不被拖垮？
  env 作为高频过滤字段进联合索引前缀（env + 业务键），两类查询天然各走各的段；真要体量到了隔离成本大于收益，升级路径是物理分表或分区表，改造点在数据访问层，业务代码无感。
- 交互卡片这种形态微信 App 都支持、Web 老版本不支持，降级渲染怎么做？
  渠道配置声明支持的形态集合与降级链（卡片→富文本→纯文本），适配引擎按"渠道能力 ∩ 答案可用形态"取最高级渲染，卡片的关键信息在富文本降级形态里必须完整承载——降级不能降级掉内容。
- 同一问题在不同渠道答案口径不一致，谁对？怎么防？
  不一致本身可能是设计（多视角答案），也可能是事故（某视角漏更新）。防的机制是知识以"问题 + 视角集合"为整体发布：发布中心校验所有启用视角都齐全且同源验证过，不允许只更新单视角就发布，改动必过完整验证。

<!-- 第五梯队：架构（55-62）选型与演进 -->

- 为什么不引入 Milvus / 专用向量数据库，向量检索放进已有的 ES 里值在哪？
  5 万级向量对专用向量库是体量误配，它解决的十亿级分片、GPU 加速全用不上，却引入一套新系统的部署、同步和运维。ES 单引擎双路让"双源数据不一致"这个问题从根上不存在——融合检索的架构复杂度被砍掉一半。
- 对比一下"pgvector 一库到底"方案，你为什么还是选 ES？
  pgvector 胜在事务一致、运维单库，中小体量完全可行；选 ES 是 BM25 质量差距——PG 的 tsvector 对中文需要额外分词插件、相关性调优生态薄弱，加上当时对亿级向量的预留和 Script Score/RRF 的引擎内融合能力。这是个可以辩论的选型，不是唯一解，面试时我会主动说另一侧的理。
- FastAPI 对比 Django / Flask，异步生态是你们最强的选型理由吗？还有别的吗？
  异步是第一理由：SSE 流式、后台导入任务、全链路 async 驱动（AsyncSQLAlchemy）都在 FastAPI 生态里原生顺路。其次 Pydantic 契约天然衔接请求校验与响应模型，OpenAPI 自动生成对多渠道对接省掉一层文档。失去的是 Django admin 这类全家桶——但知识后台我们用 Streamlit 快速搭了，成本更低。
- 用 Streamlit 搭管理后台是不是太轻？什么条件下你会换成工程化前端？
  Streamlit 赌的是"内部工具够用就好"：知识录入、发布操作、验证回放这些页面日活是坐席和运营个位数，开发成本几乎可忽略。换工程化前端的触发条件是后台开始对外（多组织租户自助运营）或出现复杂交互（批量编排、可视化检索调试），到那天再换不亏。
- 政务合规约束（数据不出域）对这个系统的技术选型产生了哪些实际影响？
  三条硬影响：embedding 必须本地推理（Sentence-Transformers 常驻而非远程 API）；检索与存储全部私有化部署，云托管 ES 方案直接出局；生成侧模型同样走私有化推理服务。合规不是选型后的检查项，是选型时的过滤器。
- 这个系统哪里体现"中台"定位？和给每个渠道各建一套问答比，收敛了什么？
  收敛在三层：知识只生产一次（双环境发布统一管口径）、检索只建设一次（融合检索多入口共用）、渲染只适配一次（渠道差异被适配引擎吃掉）。新渠道的接入成本从"复制一套系统"降为"注册一份配置"，这是中台的经济学。
- 系统当前的容量上限在哪？你怎么预估未来一年的瓶颈？
  先到的不是数据量是可用性：ES 单节点无容错，故障即检索停摆；然后是新渠道形态复杂度——Webhook 类异步接入会引入消息可靠投递问题（重推、幂等、顺序）。数据量本身按政务 FAQ 的自然增速，两年内不构成瓶颈，索引和缓存的演进路径都预留了。
- 如果再给你一条检索质量优化层，你会加什么？为什么现在没加？
  加查询理解前置层：纠错、同义词归一、多轮上下文改写——8% miss 里"全新提法"和"复合查询"两类都是它的菜。现在没加是因为性价比排序：缓存与发布体系的收益已兑现，查询理解需要语料积累，冷启动阶段先跑通主链路、让 miss 日志替我决定优化优先级。

<!-- 第六梯队：终极（63-66）复盘与灵魂拷问 -->

- 如果只能留一个非核心功能（7 类缓存、双环境发布、多渠道适配三选二淘汰其一的变体——砍掉对检索主链路最远的那个），你砍谁？
  砍多渠道适配的"实时渲染层"：检索是系统存在的理由，双环境发布是政务场景的信任底座（口径错误不可接受），都动不得；渠道形态下发可以降级为离线配置（预渲染各视角答案落库），损失灵活性但主链路无损——三块里它离"问答对不对"最远。
- 这个项目机器成本大概什么量级？哪些钱花得最值？
  私有化单机起步：CPU 推理就够（模型体量小，没为 FAQ 配 GPU），内存大头给 ES 和 Redis。最值的两笔是 embedding 本地化（省 API 费同时保延迟预算）和 Redis 缓存（DB 与 ES 的回源压力被扛掉大半）；最省钱的设计是单索引单分片——省下的都是没引入的系统的钱。
- 和后面的政务 RAG 项目比，这个 FAQ 中台的检索架构"轻"在哪、"不可替代"在哪？
  轻在知识形态：FAQ 天然短小自洽，不需要解析、分块、图谱，单引擎双路就够；不可替代在工程密度——双环境发布、7 类缓存一致性、多渠道适配这些全是 RAG 项目不碰的生产运营问题。两个项目是检索的"研究面"和工程的"运营面"，各证一半能力。
- 面试官说"这不就是 FastAPI 调 ES 开箱能力加一层缓存吗"，你怎么用 30 秒反驳？
  开箱能力只给零件：单分片性能论证、TTL 与主动失效的一致性体系、original_id 发布防重与回滚、双模型不可比时的融合策略选型、发布竞态与降级链——每一条都是开箱没有、线上必须的决策。反证很简单：把所有自研机制抽掉，系统退化成能搜不能运营的 demo，过不了政务上线评审。

## 项目亮点挖掘

1. **融合检索双路召回**
   Script Score / RRF 融合 BM25 与 dense_vector 语义检索，Sentence-Transformers 本地化推理，P99 < 200ms、Top-5 命中率 92%。
2. **7 类差异化缓存体系**
   类目树/FAQ 详情/答案视角/搜索结果/渠道配置/热门 FAQ/导航目录，5 分钟～24 小时差异化 TTL + 写操作主动失效，解决知识一致性。
3. **双环境可回滚发布**
   env 字段隔离 + original_id 溯源，测试环境配置、一键同步、正式生效，知识上线前可验证可回滚。
4. **多视角答案适配引擎**
   同一问题按微信/App/Web 渠道差异化下发文本、富文本与交互卡片，新渠道接入不改动问答核心链路。
5. **全异步高吞吐工程**
   FastAPI 全异步链路 + SSE 流式打字机交互，SQLAlchemy 2.0 批量优化支撑 5 万级导出与 3000 条异步批量导入。
6. **性能与一致性论证链**
   单分片规避归并开销、RRF 规避量纲不可比、本地推理规避网络往返——每项指标背后有可讲的调优因果，而非参数玄学。
