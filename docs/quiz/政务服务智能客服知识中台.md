## 预测押题

- BM25 全文检索和向量语义检索各自擅长什么？你的融合检索是怎么做的，RRF 和 Script Score 加权怎么选？
  BM25 擅长精确关键词/专有名词/编号匹配，向量擅长同义改写与语义泛化。单索引内双路召回后融合：BM25 与余弦分数量纲不同，RRF 基于排名融合免归一化、鲁棒性好，作为默认；需要按业务调权重且分数可比时用 Script Score 线性加权。
- 单索引单分片是出于什么考虑？数据量或并发上去了怎么演进？
  5 万级条目体量小，单分片省去跨分片归并开销、路由简单。演进路径：数据量上去按业务线拆索引或加 routing，并发上去先加副本分片再加节点。
- P99 < 200ms 怎么测出来的？慢在哪一段，你优化过什么？
  压测工具按真实查询混合打流量，统计端到端分位延迟。最慢是 embedding 推理段，优化为 Sentence-Transformers 本地常驻模型 + 批量推理，避免网络往返。
- 7 类缓存的 TTL 是怎么定的？「改了知识但线上还是旧答案」的一致性问题具体怎么解决？
  按变更频率分层：配置/类目树类稳定给 24 小时，搜索结果类高频易变给 5～15 分钟。一致性靠写操作主动失效对应 key + 缓存装饰器统一收口，下次读回源。
- 缓存主动失效失败了怎么办，有没有兜底？
  失效动作设计为幂等可重试，且所有缓存都有短 TTL 上限——即使失效消息丢失，最多 TTL 后自动收敛回源；关键路径再加版本号比对兜底。
- 测试/正式双环境发布怎么设计？original_id 溯源解决什么问题？发布失败怎么回滚？
  env 字段隔离两套记录，发布即把测试环境验证过的内容同步为正式记录，original_id 让正式记录指回来源测试记录，保证可追溯与再次同步不重复。回滚即恢复上一版正式记录或撤回测试态。
- 多视角答案适配引擎抽象了什么？新增一个渠道（比如小程序）要改哪些地方？
  抽象「答案形态 × 渠道能力」：同一知识按渠道渲染为文本/富文本/交互卡片。新增渠道只需注册渠道配置 + 实现该渠道支持的形态渲染器，检索与知识层零改动。
- SSE 流式响应和 WebSocket 怎么选？打字机体验后端做了什么？
  问答是服务端单向推流，SSE 走 HTTP 语义、自动重连、鉴权与网关链路全部复用，比 WebSocket 运维成本低。后端把生成 token 流按 SSE 事件逐帧下发，前端追加渲染成打字机效果。
- 3000 条大文件异步导入怎么保证不阻塞主流程？导入一半失败了怎么处理？
  文件落盘后立即返回，任务进后台异步队列分片解析，批量写入用 SQLAlchemy 2.0 批量链路降 ORM 开销。失败按批次回滚并记录行级错误清单供修正重传，不产生半脏数据。
- 5 万级条目高效导出用了什么手段？SQLAlchemy 2.0 批量处理链路优化了什么？
  流式分批读取（服务端游标/yield_per）+ 边读边写出，避免一次性载入内存；批量链路用 bulk insert/update 绕过逐对象 unit-of-work，导入导出吞吐显著提升。

## 项目亮点挖掘

1. **融合检索双路召回**
   Script Score / RRF 融合 BM25 与 dense_vector 语义检索，Sentence-Transformers 本地化推理，P99 < 200ms、Top-5 命中率 92%。
2. **7 类差异化缓存体系**
   类目树/FAQ 详情/答案视角/搜索结果/渠道配置/热门 FAQ/导航目录，5 分钟～24 小时差异化 TTL + 写操作主动失效，解决知识一致性。
3. **双环境可回滚发布**
   env 字段隔离 + original_id 溯源，测试环境配置、一键同步、正式生效，知识上线前可验证可回滚。
4. **多视角答案适配引擎**
   同一问题按微信/App/Web 渠道差异化下发文本、富文本与交互卡片，覆盖 15+ 接口。
5. **高并发工程吞吐**
   FastAPI 异步 + SSE 流式 + 分层架构，支撑 5 万级导出与 3000 条大文件异步批量导入。
