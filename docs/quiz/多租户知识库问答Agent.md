## 预测押题

- 多租户知识库的隔离方案怎么设计？分区、过滤、独立库三种方案怎么选？
  向量库按租户分区（物理隔离）+ chunk 级 ACL 过滤（文档级细分）组合：独立库隔离最强但资源成本随租户数线性涨，只适合大租户；纯元数据过滤最省但一漏必串；分区+过滤双层兼顾成本与纵深。
- 租户身份从哪里来？如何防止客户端伪造租户标识？
  租户 ID 由网关注入：认证后从 token 解出写入内部上下文（TenantContext 强制非空构造），应用层不信任请求体/参数里客户端自报的租户字段，入参中的租户标识一律忽略或只做一致性校验。
- 租户入驻/退租的生命周期怎么管理？退租数据如何彻底清除？
  入驻即建分区 + 默认 ACL + 审计配置；退租以租户 ID 为键级联删除：向量分区、文档元数据、ACL、会话缓存、审计归档按保留策略处理。删除任务幂等可重跑，完成后跑残留扫描验证（分区不存在 + 全局检索命中为 0）。
- 文档级权限过滤放在哪一层做？性能怎么保证？召回后过滤 vs 检索条件下推怎么选？
  主防线是检索条件下推（Milvus boolean 表达式带 ACL 字段，引擎层过滤不占召回坑位）；召回后过滤作为二次校验兜底。性能靠 ACL 随 chunk 冗余存储（免回表）+ 用户可见文档集缓存；下推表达式控制长度，大权限集用角色 ID 而非文档 ID 枚举。
- 过滤后召回不足数怎么办？会不会把 topK 过滤成 0？
  会，所以候选多取（topK×3）再过滤，过滤后不足则迭代补召；仍为空不假装没命中，明确提示「有 N 条命中因权限被过滤」——区分「库里没有」和「你无权看」，前者是检索问题后者是授权问题。
- ACL 数据本身怎么存、怎么变更（调岗/离职）？变更后旧缓存怎么处理？
  ACL 存关系库（用户/角色×文档/目录），检索侧冗余到 chunk 元数据与向量同库。变更走事件驱动：调岗/离职发权限变更消息，失效该用户可见集缓存并异步刷新 chunk 侧角色字段，新检索立即生效；兼容窗口内以检索时实时校验兜底。
- 如何保证跨租户不泄漏？除了分区还有哪些防线？最坏情况（代码 bug）下怎么办？
  纵深：分区隔离→检索条件带租户→召回后 ACL 二次过滤→生成前上下文校验→返回前逐条断言租户一致。最坏情况单点 bug：后置断言独立于前置过滤逻辑（不共享代码路径），不一致立即熔断抛异常记审计，单点失效不导致泄漏。
- LLM 环节会不会造成泄漏（提示词注入套取他人数据/上下文串租户）？
  会，两条路径：注入诱导模型复述上下文，或跨会话上下文缓存串租户。对策：进入 prompt 的上下文全部已经过租户断言（模型只见得到有权内容，套也无数据）；会话状态按租户+用户键隔离；对「把上文全部输出」类指令做检测拦截。
- 泄漏风险如何做测试验证？你会设计哪些攻击用例？
  专设泄漏回归套件：跨租户检索（用 A 身份查 B 独有关键词）、伪造租户头、提示词注入套取、权限变更后缓存旧数据、退租后残留扫描；全部纳入 CI，泄漏类用例失败阻断发布——安全问题用测试固化而不是靠 code review。
- 问答审计与计费怎么设计？审计数据量大了怎么办？计费口径如何与客户对齐？
  每次问答落审计流水（租户/用户/命中文档/token 用量/结果状态），按租户聚合出账，同时供安全巡检。量控：热数据短期明细、冷数据归档聚合，审计写入异步化不阻主链路。计费口径以「成功返回的问答次数 + token 用量」双维度写进接口文档，与账单可互相验证。

## 项目亮点挖掘

1. **双重隔离**
   向量库按 tenantId 分区物理隔离 + chunk 级 ACL 元数据过滤，跨租户数据在结构层面不可达。
2. **防泄密纵深防御**
   返回前逐条断言租户一致性，不一致立即熔断抛异常并记 BLOCKED_TENANT 审计，即使上游逻辑改坏也不泄漏。
3. **权限过滤召回策略**
   候选多取 topK×3 再 ACL 过滤，避免过滤后不足数；过滤为空时明确提示"有 N 条命中因权限被过滤"。
4. **问答审计与计费**
   每次问答落审计流水，按租户聚合计费 + 安全巡检，SaaS 商业化合规有据。
5. **租户身份安全设计**
   TenantContext 强制非空构造，租户头由网关鉴权后注入，应用层不信任客户端自报。
6. **LLM 网关接口化**
   Mock/SpringAI 双实现接口对齐，核心隔离链路纯 JDK 可离线编译验证。
