## 预测押题

- 「零运行时依赖」意味着什么？只用标准库发 HTTP 请求、管理流式响应，和用 requests / httpx 比代价在哪？
  只用 urllib/http.client + json 实现请求与 SSE 解析，安装面零依赖、无供应链风险。代价：连接池、重试、HTTP/2 等都要自己写或放弃，代码量比引库多，性能上限低——对本地/轻量场景可接受。
- 抽象基类怎么设计？Ollama 本地和 DeepSeek cloud 的接口差异在哪一层被抹平？
  基类定义 chat/stream/embed 模板方法，固定请求组装、响应解析骨架；子类只填三处差异：base_url 与鉴权头、请求体字段（Ollama 的 model/messages vs OpenAI 兼容格式）、流式帧格式。业务代码只面向基类。
- 同步异步双链路怎么做到「复用一份代码」？是两套实现还是一个引擎两种驱动？
  一个引擎两种驱动：请求构造/参数校验/响应解析全部纯函数化，只有 IO 层分 urllib 与 asyncio 两套驱动，公共逻辑零重复，两边行为用同一组用例验证。
- 密钥全走环境变量、业务代码零明文——具体怎么落地？配置文件和本地开发时怎么管理？
  配置只存环境变量名（如 DEEPSEEK_API_KEY），运行时读取，缺失则启动即报定位错误；本地用 .env + gitignore，配合模板文件标注需要哪些变量，仓库永不含真实密钥。
- 流式输出（stream）两家模型的协议差异怎么处理？
  Ollama 逐行 JSON 对象、OpenAI 兼容是 SSE data: 帧。适配层各自解析成统一的 token 增量回调接口，上层拿到的流形态一致，换后端不改消费代码。
- 超时、重试、限流这些可靠性问题在零依赖前提下你是自己实现的吗？做到什么程度？
  超时用 urllib 原生 timeout 参数；重试手写指数退避只针对可重试错误（429/5xx/网络抖动）；限流交给调用方。定位是轻量封装，不做成 tenacity，深度有限但边界清楚。
- 为什么本地选 Ollama？和 vLLM 等推理服务比适用场景是什么？
  Ollama 单机一键起服务、GGUF 量化模型 CPU/Metal 可跑，适合开发调试与隐私场景；vLLM 面向生产高并发（PagedAttention、连续批处理），部署重。开发用 Ollama、生产用 vLLM/云端 API，统一抽象让切换无感。
- 标准 src-layout 包工程指什么？为什么要为一个小库做完整的包结构？
  src/ 下放包目录 + pyproject 元数据 + 可编辑安装。好处：导入路径与安装态一致避免「本地能跑别人不能跑」，测试针对已安装包而非目录；小库也要能被其他项目正式依赖，结构是复用前提。
- 这个库后来被哪些项目复用了？（提示：与工作项目、Agent 项目的关系）
  同一抽象模式在后继项目里持续演进：file-wizard 的六提供商统一客户端就是它的多后端扩展版；Agent 项目的模型接入层也是同构思路——先把「换模型」做成配置项，后面所有项目受益。
- 如果现在让你重做，会引入依赖还是继续零依赖？取舍标准是什么？
  看使用方：内部工具继续零依赖（安装简单优于功能全）；对外发布或高并发场景会基于 httpx 重建（连接池/HTTP2/异步成熟）。取舍标准是分发成本与运行需求的平衡，不为零依赖而零依赖。

## 项目亮点挖掘

1. **零依赖封装**
   纯标准库实现 LLM 统一调用，无第三方运行时依赖，供应链面最小化。
2. **一键切换提供商**
   抽象基类统一 Ollama 本地 / DeepSeek 云端接口，业务代码不感知后端差异。
3. **同步异步双链路**
   同一份调用逻辑支持两种驱动方式，脚本场景与高并发服务场景共用一套抽象。
4. **安全与工程规范**
   密钥全走环境变量零明文；标准 src-layout 包结构，可 pip 安装、可版本化演进。
