## 预测押题

- 为什么用 LangGraph 状态机而不是线性链（Chain）或自主 ReAct Agent 做编排？有向图解决了什么控制流问题？
  调研是带条件分支的循环流程（Judge 判断要不要补检），线性链表达不了回环；自主 ReAct 控制流不确定、难测试难复现。显式图：节点承担语言任务，边承担确定性控制流，可控可单测。
- Keyword / Summary / Judge / Report 四角色怎么分工？为什么 Judge 要单独成节点？
  Keyword 生成检索词、Summary 阅读笔记、Judge 评估信息充分性、Report 综合成稿。Judge 独立是为了把「生成」与「评估」分离，避免自评偏差，也方便单独替换更严的评估策略。
- Checkpointer 断点续跑怎么实现？恢复时状态从哪加载，任务失败重跑会重复计费吗？
  每个节点执行完状态写入 Checkpointer 持久化，恢复时按 thread_id 从最新 checkpoint 继续执行，已完成节点的调用不会重跑，不重复计费。
- 迭代检索的收敛条件是什么？max_rounds 怎么定？判不收敛怎么办？
  Judge 输出「信息充分」即收敛；max_rounds 按典型主题 2-3 轮能齐的实测取余量定上限；不收敛（反复要补检）被轮数强制截断，Report 基于已有信息出稿并标注置信度降级。
- 单次检索失败为什么兜底空结果而不是中断？失败重试和降级策略怎么权衡？
  单一信息源抖动不该杀死整个长任务；缺信息会体现在 Judge 的充分性判断里自然触发下一轮补检，本身就是降级。瞬时错误做有限重试，重试耗尽才降级空结果。
- 结构化输出失败率压到 0.1% 以下具体做了什么？Pydantic 自约束模式和 function calling 什么关系？
  把 Pydantic schema 转 JSON Schema 注入模型的 function calling / tool 参数约束输出，解析后再用模型侧 schema 校验一次，失败自动修复重试。关系：Pydantic 是单一事实源，同时驱动提示约束与代码校验。
- 多用户 session 隔离怎么做的？Redis 在这里存什么，动态内存管理指什么？
  每个任务独立 session id，状态、来源列表、中间草稿全部按 session 键空间隔离存 Redis；动态内存管理指对长时间未活动/已完成会话做淘汰回收，高并发下上下文零污染。
- 置信度「基于来源时间分布确定性计算」怎么理解？为什么不用 LLM 打分？
  用来源的数量、时效分布等可复现指标算分，同样的输入永远同样的分，可解释可审计。LLM 打分既贵又不稳定，且是模型自评，对幻觉不敏感。
- 「无来源结论显式标注为模型推断」怎么实现？如何防止模型幻觉假装带来源？
  结论引用以结构化来源 ID 字段传递，程序校验 ID 必须存在于去重后的来源清单，引用不合法或无引用的结论自动标注为「模型推断」——引用合法性由代码把关而非模型自觉。
- 提示词用 Jinja2 模板集中管理，比写在代码里好在哪？怎么做灰度调优？
  提示词版本化（git diff 可读）、与控制流解耦、热更新不需改代码；5 类 Agent 模板可按版本/会话维度切换做 A/B 灰度，调优不阻塞主流程。
- 调研从 2-3 小时压到 8-15 分钟，这个量化怎么测的？报告质量人工评估过吗？
  同主题人工调研耗时与任务端到端运行时间对比得出提效区间；报告质量做过人工抽检（事实错误、来源准确性、可用性）+ 置信度与引用准确率统计，不是只看速度。

## 项目亮点挖掘

1. **状态机编排可控可测**
   LangGraph 有向图编排四角色 Agent，控制流确定性、可测试、可复现，语言任务完全下沉至 Agent 节点。
2. **断点续跑与过程可审计**
   Checkpointer 状态持久化 + on_progress 回调逐轮落盘，研究过程可回放、可断点恢复。
3. **迭代收敛机制**
   Judge 判断信息充分性驱动多轮补检，max_rounds 保证收敛，单点失败不拖垮全局。
4. **结构化输出工程**
   Pydantic 自约束把格式解析失败率压至 0.1% 以下；来源按 URL 去重、置信度确定性计算。
5. **会话级多租户隔离**
   FastAPI + Redis 实现多用户 session 上下文隔离与动态内存管理，高并发下零污染。
6. **提示词资产化**
   Jinja2 模块化模板管理 5 类 Agent 提示词，版本化、热更新、与控制流解耦。
