# 控制流与语言任务分离：一个多 Agent 编排器的设计

## 一个常见的坏味道

很多人写 Agent，第一版都是这样。

一个 while 循环，里面塞满了判断。要不要继续搜索，交给大模型决定。下一步做哪件事，也交给大模型决定。流程走到哪里，只有模型自己清楚。

这样的代码能跑，一旦出问题就麻烦了。同一个输入，跑两次结果不一样。想写单元测试，发现每条分支都要模拟一次模型调用。想知道为什么多跑了一轮，只能靠翻日志猜。

问题的根源，是把两种完全不同的东西混在了一起。

一种是控制流：循环多少次、什么时候退出、失败怎么办。这类逻辑是确定的，可以用普通代码写清楚。

另一种是语言任务：生成关键词、总结正文、判断信息够不够。这类逻辑依赖语义理解，只能交给大模型。

前者是骨架，后者是血肉。把它们揉成一团，骨架就看不见了。

## 四个角色

我给这个项目起了个名字，叫 depth-research-assistant，深度研究助手。

它的工作很单纯：给我一个研究主题，它自己去查资料，最后交一份带来源的调研报告。人工做这件事，一个主题要花两三个小时。交给它，分钟级出结果。

整个系统只有四个角色，每个角色负责一件语言任务。

- KeywordAgent：把一个研究主题拆成若干检索关键词。
- SummaryAgent：把一批搜索结果综合成一段正文草稿。
- JudgeAgent：判断现有信息是否充分，给出结论和理由。
- ReportAgent：把草稿整理成结构化报告。

四个角色之间不直接通信。它们只跟编排器打交道，各自输入一段文本，输出一段文本。

这就是第一个分离：角色之间解耦。每个 Agent 不知道别人存在，也不需要知道。想换一个更好的摘要模型，改 SummaryAgent 就够了。

## 编排器只做三件事

真正的主角是编排器，代码在 engine.py。

它的职责只有三件事：驱动循环、判断分支、记录过程。

驱动循环：先让 KeywordAgent 出一批关键词，逐个检索，把结果交给 SummaryAgent 攒成草稿。

判断分支：把草稿交给 JudgeAgent，问它信息够不够。够了就进报告环节，不够就带着新关键词进入下一轮。

记录过程：每轮结束，通过 on_progress 回调把中间状态交出去。调用方可以落盘，也可以直接显示进度。

关键在于，编排器从头到尾没有发起过一次大模型调用。

它不拼 prompt，不解析模型输出，不关心用的是哪个模型。它只调用四个 Agent 暴露出来的方法，拿到返回值，然后走下一步。所有的输入输出都是普通的数据结构，没有魔法。

这是第二个分离，也是最重要的一个：控制流与语言任务分离。

## 分离带来了什么

第一个好处是可测试。

控制流的正确性，可以用普通的单元测试保证。给编排器喂一个假的 JudgeAgent，让它前两轮返回“不够”、第三轮返回“够了”，就能验证循环次数是否精确等于三。整个过程不联网，不花钱，瞬间出结果。

如果控制流里掺了模型调用，这样的测试根本写不出来。

第二个好处是可复现。

同一个主题，同一批搜索结果，编排器的行为完全一致。只有四个 Agent 的文本输出可能有波动。排查问题时，能把“流程走错了”和“模型答偏了”区分开。这两类 bug 的修法完全不同。

第三个好处是成本可控。

调用了多少次模型、每轮花多少 token，编排器心里有数。想控制成本，改循环上限就行，不用去改 prompt。

第四个好处是模型可替换。

四个角色都用同一套抽象。本地跑 Ollama，线上换 DeepSeek，编排器一行都不用改。

## 迭代怎么收敛

自动调研最大的风险，是停不下来。

模型永远觉得信息不够，于是一轮一轮地搜下去。搜索 API 有配额，时间也有成本，不能放任。

我的做法是给循环加一个硬上限，max_rounds，默认三轮。

每一轮结束时，JudgeAgent 给出判断。如果它说信息充分，立即跳出循环，进入报告环节。如果它说不够，就用新关键词进入下一轮。到了上限还没够，也照样跳出，用当前草稿生成报告。

换句话说，模型的判断只能让循环提前结束，不能让它无限延长。收敛的保证写在控制流里，不依赖模型自觉。

这是分离带来的一个隐蔽好处：确定性代码可以兜住不确定性的边界。

## 兜底与审计

真实环境里，搜索 API 会失败，会限流，会返回空结果。

我的处理很简单：任何一次检索失败，都返回空结果，不抛出异常，不中断流程。编排器继续往下走，下一轮换个关键词再试。

一次检索失败，不该毁掉整份报告。这是容错的基本态度。

审计方面，来源按 URL 去重，避免同一篇文章被反复引用。置信度基于来源的时间分布做确定性计算，规则写死在代码里，不由模型自由发挥。

还有一个细节：没有来源支撑的结论，报告里会显式标注为“模型推断”。

调研报告最重要的是可信。宁可标注得保守一些，也不能让读者误以为每个结论都有出处。

## 中间过程要能回放

一次调研可能跑三轮，每轮都有搜索、总结、判断。如果只交出一份最终报告，用户不知道中间发生了什么。

所以我加了 on_progress 回调。每轮结束，把当前快照交给调用方，内容包括已完成的步骤、当前的草稿、已收集的来源。

调用方拿到快照，可以存进数据库，也可以推给前端做进度条。研究过程变得透明，出了分歧能回放，这也符合“来源可追溯”的产品要求。

## Prompt 也要集中管理

四个角色，五个 prompt 模板，全部放在 Jinja2 文件里。

- keyword：生成检索关键词。
- summary：综合搜索结果。
- judge：判断信息充分性。
- report：生成 Markdown 报告。
- report_html：生成 HTML 版本。

模板独立成文件，好处是调优时不碰控制流代码。改一句措辞，就在模板里改。控制流的逻辑，一行不用动。

这也是分离思想的延伸：可变的部分和不变的部分，放在不同的地方。

## 对应业界的什么模式

这套设计不是原创。

Anthropic 有一篇文章，叫《Building Effective Agents》。它把这类结构称为 orchestrator-workers 模式：一个主控负责拆分和调度，若干个 worker 负责具体的语言任务。

LangGraph 把它抽象成图：节点是 Agent，边是控制流，conditional_edges 就是我的 if 分支，checkpointing 就是我的 on_progress。

区别在于，我这个版本是裸写的。没有框架依赖，十几行控制流代码一眼看完。代价是没有持久化、没有断点续跑、没有人机中断这些高级能力。

什么时候该上框架，什么时候手写就够，我现在的判断是看节点数量。五个节点以内的确定流程，手写更透明，调试也更快。节点再多，或者需要在流程中间暂停、恢复、人工介入，框架的价值就出来了。

## 小结

这个项目我最大的收获，是理解了“控制流与语言任务分离”这条原则。

具体做法不复杂：编排器只写确定性代码，四个 Agent 只做大模型调用，两者通过普通数据结构交换信息。

好处是一串的：流程可测试、行为可复现、成本可控、模型可替换、边界能兜住。

反过来说，如果一个多 Agent 系统让我看不出“流程走到哪一步是确定的”，我会先怀疑它的设计，而不是先怀疑模型。

确定性是工程的地基。模型只是站在地基上的那个人。
