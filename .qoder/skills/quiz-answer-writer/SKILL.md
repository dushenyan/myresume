# 通俗风格问题解答（阮一峰风格）

核心使命：**把任何一个问题，讲到没接触过的人也能听懂**。答题优先讲透道理，文件机制只是题目来自本仓库押题库时的附加规范，不要让它束缚作答。

## 两种模式

| 模式 | 触发条件 | 产出 |
| --- | --- | --- |
| A · 通用作答 | 用户抛出任一问题（技术概念、面试题、原理、"为什么 X 会 Y"），未涉及押题库文件 | 直接在对话或用户指定文件中输出完整详解，遵循下方「通俗化铁律」 |
| B · 押题外置 | 题目来自 `docs/quiz/project|skill/*.md`，或用户要求「改成单独文件」「外置详解」 | 撰写 `docs/quiz/answers/<uuid8>/ans.md` + 回写题包 `@answer:` 引用 + 解析器校验，同时遵循「通俗化铁律」与「模式 B 文件硬规则」 |

模式 A 与模式 B 的**写作部分完全一致**；模式 B 只是多了文件落位与引用校验。

## 通俗化铁律：阮一峰风格（两种模式都必须遵守）

目标是「通俗易懂」，硬性遵循以下每一条：

1. **开头必给「一句话」导语**，用引用块：`> 一句话：……`，先抛结论再展开。
2. **三段式递进**：先讲「它是什么」，再讲「为什么需要它」（没有它会遇到什么麻烦），最后讲「怎么用 / 怎么落地」。不许一上来就堆实现细节。
3. **从生活化场景切入**，每个核心概念配一个日常类比：如「假设领导让你调研一个政策主题，你会怎么干？」「缓存就像你把常用书放在桌面上，而不是每次去图书馆」。类比要在正文早期出现，不能塞在末尾当点缀。
4. **多用衔接词**：「换句话说」「举个例子」「也就是说」「你想过没有」「值得注意的是」。
5. **短句优先，短段落**：一段只讲一个点；长定语从句拆成两三句短句，不贪多。
6. **术语首次出现必解释**：中文解释 + 英文原名，绝不允许用一个术语去解释另一个术语。
7. **配一段可运行的示例代码**（Python/伪代码/JSON 配置均可），代码下用一句话点出它在讲什么；代码内的注释必须放在行首独立一行（上一行注释），不得跟在语句尾部——窄屏会把行尾注释折行错位。
8. **专门回答「面试官/追问者真正想考的点」**：用「关键问题：……」小标题挑出最容易被追问处，分层说透（现象 → 原因 → 解法 → 代价）。
9. **结尾「## 小结」**：3~5 条要点式提炼，每条本身也要是大白话。
10. **小结末尾追加「一句话收口」**：用引用块给一句可直接口述、浓缩全篇的收尾话术。
11. **禁用百科腔**：不写「X 是一种广泛应用于……的机制/框架」这类定义堆砌；不写无主语的被动长句；全篇像在给同事当面讲解。

### 一句话收口模板

```markdown
> **一句话收口**：<把本题最核心的 2~3 个卖点浓缩成一句，读完能直接背出来应答>。
```

## 作答流程

```
- [ ] 1. 吃透问题本身：明确题目在问什么、答到什么深度算「讲透了」
- [ ] 2. 收集事实来源：
      · 模式 A：涉及用户简历上的项目/技术经历时，先读对应材料对齐口径；纯通用问题跳过
      · 模式 B：读题包文件与目标题目行（确认当前行号，文件常被扩充过），拿到该题 `@frame` 的 uuid 前八位
- [ ] 3. 结合作答的项目不能凭空编：见「选定项目与上下文抽取」，动手前用 AskUserQuestion 让用户确认
- [ ] 4. 按「通俗化铁律」写详解：问题 → 生活类比 → 原理分层拆解 → 示例代码 → 关键问题 → 小结 → 一句话收口
- [ ] 5. 仅模式 B：把题包对应题目的行内解答替换为一行 `  @answer: <uuid8>/ans.md`，保留原 `@frame:` 行于其下方
- [ ] 6. 仅模式 B：用 esno 跑解析器校验（题数不变、引用能读通、无乱码），临时脚本跑完删除
```

## 模式 B 文件硬规则

**一道题 = 一个目录 = 一份 `ans.md`**，目录名取该题 `@frame:` 演示 uuid 的**前八位**：

```
docs/quiz/answers/086b8c26/ans.md     ← @frame: 086b8c26-7fe8-4585-a7cb-7a55ac8df1f4
docs/quiz/answers/4c49c76c/ans.md     ← @frame: 4c49c76c-f27b-4ca3-baf7-b52127cf05e9
```

题包引用行与目录一一对应：

```
- Elasticsearch 8.x 在这里承担什么角色？dense_vector 字段是干什么的？
  @answer: 086b8c26/ans.md
  @frame: 086b8c26-7fe8-4585-a7cb-7a55ac8df1f4
```

- 目录名必须与该题 `@frame` 的前八位完全一致，便于从演示站反查到本地详解；
- 目录内答案文件**只叫 `ans.md`**，不取语义化文件名；同目录可再放配图、脚本等附属素材；
- `@answer:` 写在 `@frame:` 上方一行（先答案后演示，与既有题包顺序一致）；
- 题目**没有 `@frame`** 时（未挂在线演示），退回旧的扁平语义化文件 `answers/<slug>.md`，别硬编一个假 uuid 目录；
- 改造前已存在的扁平文件（如 `iterative-convergence.md`）保持原样，两种写法解析器都吃。

### 关键格式约束

- 题包里**顶格 `- ` 是题目，缩进行是参考解答**；引用行写成两空格缩进的 `  @answer: <uuid8>/ans.md`。
- 引用行支持一层目录相对路径（解析器允许 `@answer:` 里带 `/`），绝对路径与含 `../` 的穿越路径被 `readQuizAnswerHtml` 统一拦下；路径写错只会让详情视图提示读取失败，不会往目录外读文件。
- 详解文件顶部 `---` front-matter 与首个 `# 一级标题` 渲染时会被剥离（详情视图已含标题区），但**仍要写**，便于离线阅读；
- **front-matter 的 `title` 与首个 `# 一级标题` 必须与题包原始题干逐字一致**（保留原始引号"、全角问号？等标点，不得简写或改写），否则离线打开文件会觉得标题缩水；
- 支持的语法：`## ~ ####` 标题、有序/无序列表、`` `行内代码` ``、围栏代码块、**粗体**、*斜体*、`> 引用`、`---`、图片/链接（仅 http(s) 或站点绝对路径）；
- 字典/配置类代码块每个关键键行首配一行用途注释；JSON 示意块用 ```jsonc 围栏才能写 `//` 注释。

## 选定项目与上下文抽取（关键，勿写死）

详解若涉及用户的项目经历，必须**扎根到用户指定的那一段项目经历**上，绝不能凭空套某个固定项目。模式 B 默认从题包自身 `matchName` 推断对应项目，但**动手前先用 AskUserQuestion 让用户确认或改选**要结合作答的项目（跨项目引用、或题包未绑定项目时尤其要问）。

### 步骤

1. **列出候选项目**：从 `src/data/projects.ts` 与 `src/data/personalProjects.ts` 读取各项目 `displayName`；若处理的是某个题包，默认把其 front-matter `matchName` 对应项作为首选。
   ```bash
   grep -nE "displayName:|name:" src/data/projects.ts src/data/personalProjects.ts
   ```
2. **让用户选**：用 AskUserQuestion 把候选 `displayName` 做成选项（推荐项放第一位、标注「(推荐，题包默认绑定)」），由用户决定这道题结合哪个项目作答。
3. **抽取该项目真实上下文**：读该项目的 `summary` / `description` / `responsibilities` / `primaryLanguage` 全量字段，以及对应题包 `docs/quiz/project/<项目>.md`（或技能题包 `docs/quiz/skill/<主题>.md`）里的既有问答与亮点，作为作答的事实来源。
4. **对齐口径**：详解里出现的框架、参数、量化数据（如失败率、耗时、轮数）必须与简历 `responsibilities` 及题包既有解答一致，避免面试时对不上。

> 通用原则：不预设任何具体项目。以下「示例」仅为「多 Agent 深度研究助手」一次性示范，换项目时**整段替换**，不要照搬。

### 示例（仅示意，非默认）

以「多 Agent 深度研究助手」为例，抽取到的锚点会是：LangGraph 有向图 + 条件边、四角色 Keyword/Summary/Judge/Report、Checkpointer + `thread_id` 恢复、`max_rounds` 兜底收敛、Pydantic 结构化输出失败率 < 0.1%、Redis session 隔离、Jinja2 模板灰度。若用户选的是「政务 RAG」，则换成 GraphRAG 三存储、两阶段检索 + Rerank、RAGAS 回归等锚点。

## 反例

- ❌ 百科定义腔开头（「RAG 是一种检索增强生成技术，广泛应用于……」），全程无类比、无场景，读者看完更糊涂——违反通俗化铁律第 2、3 条。
- ❌ 用术语解释术语（「用 Embedding 把 token 映射到 latent space」），首现术语不给中文解释。
- ❌ 只做「把简答复制进新文件」——没有阮一峰式的场景铺垫与「关键问题」拆解。
- ❌ 忘记在题包保留 `@answer:` 行，或缩进不对导致被解析成新题目。
- ❌ 把某个项目的技术事实写死当成通用默认，未让用户选项目就照搬。
- ❌ 脱离所选项目事实吹嘘不存在的实现（面试一问细节就崩）。
- ❌ 漏掉「## 小结」后的「一句话收口」。
- ❌ ans.md 标题自己简写（题干是「Elasticsearch 8.x 在这里承担什么角色？」却写成「ES 的角色」）——必须逐字照抄题干。
- ❌ 目录名与题目 `@frame` uuid 前八位对不上，或把答案文件命名成 `answers/086b8c26/es-role.md` 这种语义名（必须叫 `ans.md`）。
- ❌ 又新建 `answers/<uuid8>.md` 扁平文件——同一题只允许一个入口，要么目录 + `ans.md`，要么无 `@frame` 时的语义化 `slug.md`。
- ❌ 把代码注释跟在语句尾部对齐写（如 `"page_start": 3,  # 起始页`）——窄屏折行后注释与键对不上，改成上一行行首注释。
- ❌ 模式 A 的通用问答硬套模式 B 的 uuid 目录、解析器校验——题目不来自押题库就不要动 `docs/quiz/` 里的任何文件。
